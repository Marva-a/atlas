why: New flaws appear daily, so this is continuous work. Exam scenarios ask what to do next: scan, prioritize, fix, verify or report.
plain: Vulnerability management is like regular building maintenance. You inspect, decide what is urgent, fix it, check the fix and keep records.
tech: Identification methods include scanning with vulnerability tools; Internet Protocol Address Management (IPAM), which tracks address use and can reveal unknown hosts; cloud security posture management (CSPM), which finds cloud misconfigurations; and source code review. Credentialed scans sign in for more accurate results, and non-credentialed scans show what an outsider would see.
tech: Prioritization uses severity assessment plus context, and penetration test report review, which shows what was actually exploitable. Remediation may mean patching, changing configuration, applying a compensating control or formally accepting the risk. Verification confirms the fix, usually by rescanning.
tech: Reporting can be internal, to management and asset owners, or external. External routes include a bounty program, which pays researchers for valid findings, and responsible disclosure policies, which tell researchers how to report safely. A false positive is a reported problem that does not exist. A false negative is a real problem that was missed.

term: External == Reporting outside the organization.
term: Bounty program == Paying researchers for valid vulnerability reports.

plain: Monitoring is like a building's security desk. Cameras, door sensors and alarms all feed one room. A SIEM is that room. Alert tuning makes sure the alarm does not go off each time someone opens a window.
tech: Monitoring covers systems, applications and infrastructure. Activities include log aggregation (collecting logs in one place), alerting, scanning, archiving (retaining data for later), reporting and alert tuning (adjusting rules to reduce false positives).
tech: Tools include benchmarks, which define secure configuration targets; agents, installed on a device, and agentless collection, which reads remotely; security information and event management (SIEM), which aggregates and correlates events; antivirus; DLP; vulnerability scanners; orchestration; and a packet analyzer such as Wireshark, which examines traffic in detail. tech: Protocols: NetFlow records metadata about traffic flows but not content. Simple Network Management Protocol (SNMP) monitors and manages devices. syslog is a standard for sending log messages. Security Content Automation Protocol (SCAP) standardizes how vulnerability and configuration information is expressed, so tools can share it. Port mirroring copies traffic to a monitoring port. Dashboards summarize status. Automated alerts notify staff without someone watching. Network management systems monitor device health.

title: Identity: accounts, federation, SSO, SAML, LDAP, OAuth and OIDC

out: Manage accounts from provisioning through deprovisioning.
out: Explain federation and single sign-on.
out: Clearly distinguish SAML, LDAP, OAuth and OpenID Connect.
why: Identity is now the main security boundary, and stolen or over-privileged accounts are behind many breaches. The difference between OAuth and OIDC trips up even experienced people.
plain: Federation is like using your passport in another country: a government you trust vouches for you. Single sign-on is a wristband at a festival: show it once and you can enter each stage.
plain: OAuth is a hotel key card: it says what doors you can open, not who you are. OpenID Connect adds a photo ID on top: it tells the application who you are.
tech: Provisioning creates accounts and grants access. Deprovisioning removes them, and should happen promptly when someone leaves. Permissions assignments have implications: granting a permission to a group affects everyone in it. Identity proofing verifies a person is who they claim to be before issuing credentials. Federation allows trust between organizations, so that a person can use one identity across them.
tech: Single sign-on (SSO) lets a user authenticate once for many applications. Security Assertions Markup Language (SAML) exchanges XML assertions between an identity provider and a service provider, and is common in enterprise SSO. Lightweight Directory Access Protocol (LDAP) queries and manages directory information such as users and groups. Open Authorization (OAuth) is an authorization framework: it grants an application limited access to resources on a user's behalf using access tokens. OAuth by itself does not tell an application who the user is.
tech: OpenID Connect (OIDC) is an identity layer built on OAuth 2.0. It adds an ID token, a signed statement about who authenticated. Use OIDC to sign users in, and OAuth to grant access to an API. OIDC does not appear in the current exam list by name, but it is essential to understanding OAuth correctly.
tech: Account types include user accounts; privileged accounts, either global (rights across an environment) or local (rights on one system); service accounts for applications; third-party accounts for outside organizations; and emergency access accounts, sometimes called break-glass accounts, which are tightly controlled, used only in emergencies and closely monitored.

out: Compare access control models.
out: Choose MFA factors and understand their strengths.
out: Apply current password guidance.
why: Most identity attacks succeed through weak or reused credentials and excessive permissions. Picking the right model and factors closes those paths.
plain: Role-based access is like staff uniforms: nurses get nurse access. Discretionary access is like owning your diary: you decide who reads it. Mandatory access is like a military clearance, which the owner cannot change. Just-in-time access is a key checked out for one hour.
tech: In role-based access control, users are assigned roles, roles hold permissions, and a person's access is the combination of their roles. With role inheritance, a senior role automatically receives the permissions of a junior role, so an administrator role can include everything an editor can do. Least privilege means giving each role only what the job needs. Access enforcement must happen on the server for every request: hiding a button changes what users see, not what they can do.
tech: Access control models include role-based (permissions follow job roles), rule-based (conditions apply, such as firewall rules), mandatory (the system enforces labels and clearances), discretionary (owners decide), time-based (access is limited to certain hours) and just-in-time (elevated access is granted temporarily when needed). Attribute-based access control (ABAC), which decides using attributes of the user, resource and context, is not in the current list but is common. Privileged access management (PAM) tools secure and broker admin access.
tech: Access management includes authentication, and policies that are logical/technical (enforced by systems) or administrative/business (rules set by the organization). An access review periodically confirms that people still need their permissions.
tech: Multifactor authentication uses different factor types. A hard token is a physical device. A soft token is an app. Biometrics measure a body feature. A one-time password (OTP) is valid once or for a short time. A backup code is a pre-generated recovery code. Phishing-resistant options such as FIDO2 security keys and passkeys are stronger than SMS or push prompts.
tech: Password concepts: a passkey is a FIDO credential based on public key cryptography, bound to the real site, so it resists phishing. Passwordless authentication replaces passwords with such methods. Password managers generate and store unique passwords. NIST SP 800-63B-4 says that passwords used alone must be at least 15 characters, and that verifiers should check against lists of compromised values, should not impose composition rules and should not force periodic changes unless there is evidence of compromise. Many organizations still enforce complexity, expiration and minimum age, and the exam may refer to them. Password best practices cover length, complexity, reuse, expiration, age (how long a password must be kept before it can be changed), compromised credential monitoring, account auditing and a policy report that shows compliance.

out: Name the four OAuth roles and what each one does.
out: Follow the Authorization Code flow with PKCE step by step.
out: Explain access tokens, refresh tokens, scopes, expiry and revocation.
out: Decide when OIDC, Authorization Code, Client Credentials or the Device flow fits.
why: Almost every modern product connects to other products. OAuth decides how much access those connections receive and how that access ends, so misunderstanding it leads to over-granted, long-lived access that nobody can see.
plain: Imagine lending a parking valet a key that starts the car but cannot open the boot, and that stops working at midnight. You never hand over your own key. OAuth works like that: an app receives a limited, expiring pass instead of your password. OpenID Connect adds a signed note saying who you are.
tech: OAuth 2.0 defines four roles. The resource owner is usually the user. The client is the application that wants access. The authorization server authenticates the user, records consent and issues tokens. The resource server is the API holding the data, and it accepts or rejects tokens. Scopes name what the client may do, such as reading a calendar, and the granted scopes can be narrower than those requested.
tech: In the Authorization Code flow the client sends the browser to the authorization server. The user signs in and approves the request. The browser returns to a pre-registered redirect URI with a short-lived, single-use code. The client then exchanges that code at the token endpoint, over a back channel, for tokens. Exact matching of the redirect URI stops an attacker from sending the code somewhere else.
tech: Proof Key for Code Exchange (PKCE) protects that code. The client creates a random code verifier, sends a SHA-256 hash of it as the code challenge at the start, and reveals the verifier only when exchanging the code. An attacker who steals the code cannot produce the verifier. The current OAuth security best practice, RFC 9700, requires protection against code injection and recommends PKCE for all clients, including ones with a secret. It also says the Implicit grant should not be used and the Resource Owner Password Credentials grant must not be used.
tech: An access token is presented to the resource server and should be short-lived and narrowly scoped. A refresh token lets the client get a new access token without asking the user again, is sent only to the authorization server, and should be rotated or sender-constrained for public clients. Expiry is automatic. Revocation ends access early, as RFC 7009 describes. A self-contained JSON Web Token (JWT) access token can often keep working until it expires, even after revocation, unless the resource server checks with the authorization server. That is one reason lifetimes are kept short.
tech: The Client Credentials grant is for one service talking to another with no user present. The Device Authorization grant suits input-limited devices such as televisions. OpenID Connect adds authentication on top of OAuth: requesting the openid scope returns an ID token, a signed JWT intended for the client, that states who authenticated. An ID token should not be sent to APIs, and an access token should not be treated as proof of who signed in.

walk: Follow Authorization Code with PKCE
- The client creates a random code verifier and hashes it to make a code challenge.
- The client redirects the browser to the authorization server with its client ID, redirect URI, scopes, state value and code challenge.
- The user signs in and approves the scopes.
- The authorization server redirects back to the registered URI with a single-use code.
- The client checks the state value, then posts the code and the original verifier to the token endpoint.
- The authorization server hashes the verifier, compares it with the challenge and issues tokens.
- The client calls the resource server with the access token.

scenario: A single-page app needs to read a user's documents through an API on that user's behalf. A developer suggests collecting the user's password and sending it to the API. What should be used instead?
answer: The Authorization Code flow with PKCE and a narrow read scope. The app never handles the password, access is limited and expiring, and the user or an administrator can revoke it. The password grant must not be used.
q 4.5 mcq e | OAuth roles | In OAuth 2.0, which component accepts or rejects access tokens when an API is called?
+ The resource server :: It hosts the API and checks each token presented.
- The authorization server :: It issues tokens, but the API call goes elsewhere.
- The client :: It presents tokens and does not judge them.
- The resource owner :: The owner grants consent and does not check tokens.
q 4.5 mcq m | PKCE | What does PKCE specifically protect against?
+ Use of a stolen authorization code :: The thief cannot supply the original code verifier.
- A weak user password :: PKCE does not change password strength.
- A forged TLS certificate :: Certificate validation handles this.
- A user approving too many scopes :: Consent design and policy handle this.
q 4.5 mcq m | Token purpose | Where should a client send a refresh token?
+ Only to the authorization server :: It is exchanged there for new access tokens.
- To every API it calls :: This exposes a powerful credential widely.
- To the resource owner's browser storage for sharing :: This would increase exposure.
- To the identity of the next client :: Tokens are not passed between clients.
q 4.5 mcq h | Revocation | An administrator revokes an integration, but its self-contained JWT access token still works for ten more minutes. What explains this?
+ The API validates the JWT locally until it expires :: Local validation does not consult revocation state.
- Revocation always requires a server restart :: Restarting is not part of revocation.
- The refresh token has become an ID token :: Tokens do not change type.
- OAuth does not support revocation at all :: RFC 7009 defines token revocation.
q 4.5 match m | Choosing a flow | Match each situation to the best OAuth choice.
= A nightly job calls an API as itself => Client Credentials
= A mobile app acts for a signed-in user => Authorization Code with PKCE
= A television shows a code to enter on a phone => Device Authorization
why: Ask who is acting, and whether that party can use a browser and hold a secret.
q 4.5 tf e | ID tokens | True or false: an ID token should be sent to an API as proof of access.
- True :: APIs should receive access tokens.
+ False :: An ID token is intended for the client and describes authentication.
mistake: Treating a successful OAuth grant as proof of who the user is. Use OIDC for sign-in.
mistake: Assuming revocation stops every token instantly.
