OAuth 2.0 and OpenID Connect in plain words

Day 22 · Week 4 · Intermediate · about 120 min

OAuth lets one app use another on your behalf without your password; OpenID Connect adds a standard way to say who you are, and together they power “Sign in with Google”.

By the end, you can: Explain the distinction between OAuth 2.0 authorization and OpenID Connect authentication, and identify which token (ID vs access) serves which purpose.

Why it matters to a designer

Consent screens, “Sign in with” buttons, connected apps and admin settings for them all come from OAuth and OpenID Connect. Designers who understand the flow can design clearer consent, better errors and safer defaults, and can work with engineers as equals.

Key ideas

  • You already know (Week 1) the difference between authentication and authorization. OAuth is about authorization; OpenID Connect adds authentication on top.
  • The valet key picture: you give a parking valet a key that only starts the car and opens the door, not the boot. OAuth gives an app a limited key (a token) instead of your password.
  • Four roles: the resource owner (you), the client (the app asking), the authorization server (which issues tokens, like Google’s sign-in) and the resource server (the API with your data).
  • The authorization code flow: the app sends you to the sign-in page, you sign in and approve, the app gets a short code, then swaps it for tokens behind the scenes. PKCE adds a one-time secret so a stolen code is useless.
  • Three tokens: an access token (the key for the API, short-lived), an ID token (who you are, from OpenID Connect) and a refresh token (gets new access tokens without signing in again).
  • Tokens are often JWTs: three parts (header, payload, signature). The payload is encoded, not encrypted, so anyone holding the token can read it.
  • Current best practice: use the authorization code flow with PKCE, avoid the old implicit and password grants, and be careful where browser apps store tokens.

Key terms

OAuth 2.0A standard that lets an app access something on your behalf with a limited token.
OpenID Connect (OIDC)A layer on OAuth that tells the app who you are, with an ID token.
clientThe app asking for access.
authorization serverThe service that signs you in and issues tokens.
scopeWhat the app is asking to do, such as “read your calendar”.
consent screenThe page where you approve what an app may do.
access tokenA short-lived key the app uses to call an API.
refresh tokenA longer-lived token used to get new access tokens.
PKCEProof Key for Code Exchange: protects the code in the sign-in flow from being stolen and reused.
JWTJSON Web Token: a signed token with a readable payload.

What a good answer looks like

  • You give the valet a limited key that only does certain things, not your house keys. OAuth gives an app a limited, revocable token for specific actions instead of your password.
  • The access token lets the app call an API for a short time. The ID token tells the app who you are. The refresh token gets new access tokens without asking you to sign in again.
  • It is only encoded, not encrypted. Anyone who holds the token can decode and read it. The signature proves it was not changed, not that it is private.
