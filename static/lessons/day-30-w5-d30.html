Kubernetes networking and network policy

Day 30 · Week 5 · Part of the Network and Kubernetes Security pathway · Intermediate · about 120 min

By default every pod in a Kubernetes cluster can talk to every other pod; network policies are the rules that limit this, and tools like Calico enforce them.

By the end, you can: Explain how a Kubernetes NetworkPolicy selects Pods by label, and state that enforcement requires a supporting network plugin such as Calico.

Why it matters to a designer

This is the problem Tigera exists to solve, and the heart of case study 2. Platform engineers know default-allow is risky, but switching to default-deny can break apps. Designers help them see traffic, write policies safely and roll them out with confidence.

Key ideas

  • From Week 3 you know access rules for people and devices. Network policy is the same idea for services inside a cluster.
  • Kubernetes finds things by labels, like name tags: app=orders, team=payments. A network policy picks pods by label, not by name or address, because pods come and go.
  • A Service gives a group of pods one stable name and address, so web can always reach “orders” even as pods restart.
  • Default allow: in a namespace with no NetworkPolicy selecting a pod, everything can reach it. This default-allow behaviour, and NetworkPolicy enforcement itself, both depend on the cluster running a network plugin (CNI) that supports NetworkPolicy, such as Calico — without one, a NetworkPolicy you write is simply not enforced, even though Kubernetes accepted it.
  • A network policy says, for example: “pods labelled app=payments-db accept traffic only from pods labelled app=payments on port 5432.” Once a pod is selected by any policy, everything else to it is denied.
  • Calico (open source, by Tigera) enforces network policies and adds its own features. Cloud security groups are stateful: if a request is allowed in, its reply is allowed out automatically.
  • Mutual TLS (mTLS) is TLS where both sides prove who they are, not only the server. Service meshes use it so each service knows exactly which service is calling.

Key terms

labelA key-value tag on a Kubernetes object, such as app=orders.
selectorA rule that picks objects by their labels.
ServiceA stable name and address for a group of pods.
network policyA Kubernetes rule that limits which pods can talk to which.
ingress and egressTraffic coming in to a pod, and traffic going out of it.
CalicoTigera’s open-source networking and network security for Kubernetes.
statefulA firewall that remembers allowed connections and lets their replies through.
mTLSMutual TLS: both sides of a connection prove who they are.
service meshA layer that manages and secures traffic between services, often with mTLS.

  • What does “default allow” mean, and why is it risky?
  • How does mTLS differ from ordinary TLS?

What a good answer looks like

  • Pods are created and destroyed all the time and get new names and addresses. Labels describe what a pod is (app=orders), so a policy keeps working as pods change.
  • With no policies, every pod can reach every other pod. If one service is compromised, the attacker can move freely to databases and other services.
  • In ordinary TLS only the server proves who it is. In mTLS both sides do, so the server also knows exactly which client or service is calling.
