Exercise 8: an OIDC sign-in, step by step

Day 24 · Week 4 · Intermediate · about 120 min

You will sign in to a sample app through your Keycloak and watch every redirect, code and token in the browser’s developer tools.

By the end, you can: Follow an OIDC authorization-code flow in the browser and identify its visible steps (redirect, consent, callback, token).

Why it matters to a designer

Seeing the flow with your own eyes turns abstract diagrams into screens and moments. You will know where users wait, where errors appear and what engineers mean by “the redirect URI is wrong”, which makes your designs and conversations much stronger.

Key ideas

  • Developer tools (in Chrome or Firefox) show every network request your browser makes. The Network tab is where you will watch the sign-in.
  • You will see: the app redirect to Keycloak (with client_id, scope and code_challenge), your sign-in, a redirect back with a code, and a request that swaps the code for tokens.
  • The redirect URI must exactly match what is registered in Keycloak. A one-character mismatch is one of the most common setup errors.
  • You can paste an ID token into a JWT decoder to read its claims: who you are (sub, email), who issued it (iss) and when it expires (exp).
  • Watch it as a designer: which screens does the user see, which happen invisibly, and where could they get stuck?

Key terms

redirect URIThe address the identity provider sends the user back to after sign-in.
client IDThe public name of an app registered with the identity provider.
claimA piece of information inside a token, such as email or expiry time.
developer toolsBrowser tools that show network requests and page details.
code challengeThe PKCE value sent at the start of the flow to protect the code.

Check yourself

  • What does the redirect URI do, and what happens when it is wrong?
  • Which steps of the sign-in are invisible to the user?

What a good answer looks like

  • It is where the identity provider sends the user back with the code. If it does not match exactly, the provider refuses, and the user sees an error that usually means nothing to them.
  • The code exchange for tokens and token checks happen behind the scenes. The user sees only the app, the sign-in page and maybe a consent screen.
