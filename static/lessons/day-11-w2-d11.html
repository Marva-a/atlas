Exercise 4: map your tailnet, sharing, and when access control fails

Day 11 · Week 2 · Basics · about 210 min

You will look at your network the way an admin does (users, devices, names and who can reach what), then at what happens when an app checks who you are but not what you may reach.

By the end, you can: Read a Tailscale device inventory, explain what MagicDNS and sharing each do, find a usability gap in removing access, explain broken access control and BOLA with an example, and tell an authentication failure from an authorization failure.

Why it matters to a designer

Admins think in inventories: what is on my network, who owns it, and is anything there that should not be? Sharing, roles, exports and impersonation are also where authorization most often fails after a perfectly good sign-in. Designers who see both make the picture clear at 3 devices or 3,000, and spot risky sharing flows before they are built.

Key ideas

  • The admin console lists machines (devices) and users. Each machine has an owner, an address, a name, an operating system and a “last seen” time.
  • MagicDNS gives every device a name, so people type “laptop” instead of 100.101.102.103. Names are easier for humans and safer in rules.
  • Sharing gives one device to someone outside your tailnet, without giving them the whole network. Example: sharing a home server with a friend.
  • Removing access matters as much as giving it: look at how easy it is to un-share a device or remove a user, and what the product tells you when you do.
  • Technical users often use the command line instead of the console. A good product keeps both views consistent.
  • Sharing is an authorization decision. Authentication says who you are; authorization says what you may do (Day 2). Most serious app flaws are authorization failures that happen after a perfectly good sign-in.
  • Broken object level authorization (BOLA, also called IDOR): you open /invoices/1041, change it to /invoices/1042 and see another customer's invoice, because the server checked that you were signed in but not that the invoice was yours.
  • OWASP's web Top 10 has put broken access control first in its recent editions. Other entries include security misconfiguration, cryptographic failures, injection, insecure design, authentication failures, software supply-chain failures, and logging and alerting failures.
  • Injection: the app treats user input as instructions. Classic example: text typed into a search box is run as part of a database query. Prompt injection in AI products (Day 51 and the AI Security pathway) is a close cousin.
  • Insecure design is a flaw in the idea, not the code: a password reset that emails the new password, or an export that includes every customer's data. These are cheapest to fix in design.
  • Design levers: every object has a clear owner and sharing rule; permission checks are described per action, not per screen; admin impersonation is visible and logged; bulk actions and exports have their own permissions.
  • Error messages leak too: 'no account with that email' tells an attacker which emails exist. A neutral message ('if an account exists, we sent a link') protects users with little cost.

Key terms

machineA device in your tailnet: laptop, phone, server.
MagicDNSTailscale’s feature that gives every device a readable name.
sharingGiving one device to someone outside your tailnet.
last seenWhen the device last connected; useful for finding old devices.
inventoryA full list of what is on the network and who owns it.
CLICommand-line interface: controlling a product by typing commands.
broken access controlWhen users can act outside their permissions, such as viewing or changing data that is not theirs.
BOLABroken object level authorization: an API returns an object without checking that the caller may see it. Also called IDOR.
injectionWhen untrusted input is treated as instructions, such as text run as part of a database query.
insecure designA security flaw in how a feature was designed, not in how it was coded.
OWASP Top 10A widely used list of the most critical web application security risks, updated every few years.
account enumerationFinding out which accounts exist from differences in a system's responses.
impersonationAn admin or support feature that lets staff act as a user; risky if not visible, limited and logged.

Check yourself

  • Why are device names safer than IP addresses in rules and lists?
  • How is sharing a device different from adding someone to your tailnet?
  • What would an admin with 500 devices need that you did not need with 2?
  • A user is signed in and changes a number in the address bar to see another company's report. Is that an authentication or an authorization failure? Why?
  • Name two design decisions in a sharing feature that could lead to broken access control.
  • Why is a message like 'No account found for this email' a security problem?

What a good answer looks like

  • People read and remember names, so mistakes are easier to spot, and names can stay the same when addresses change.
  • Sharing gives access to one device only; adding someone to the tailnet makes them a member whose access is set by your rules. Sharing is narrower and easier to revoke.
  • Search, filters (by owner, tag, last seen), bulk actions, clear signs of old or unknown devices, and a way to see who can reach what without reading every rule.
  • Authorization. The server knew who the user was (authentication worked) but did not check that this report belonged to their company. This is broken object level authorization (BOLA or IDOR).
  • For example: link sharing that defaults to 'anyone with the link'; guests who can re-share; an export that ignores row-level permissions; admins who can impersonate users without it being shown or logged; roles that are checked per screen instead of per action.
  • It lets an attacker find out which email addresses have accounts (account enumeration), which helps targeted phishing and password guessing. A neutral message gives the same answer either way.
