Machine identities, secrets and workload identity

Day 50 · Week 8 · Advanced · about 120 min

Software also needs identities: services, scripts and pipelines sign in with keys, tokens and certificates, and today these machine identities far outnumber people.

By the end, you can: Explain why a machine or workload needs its own scoped identity rather than a shared long-lived credential.

Why it matters to a designer

Many breaches start with a leaked API key, not a stolen password. Security companies, including network and Kubernetes security vendors, are building products for machine identity, and designers must make invisible things visible: which keys exist, who owns them and what they can reach.

Key ideas

  • You know how people prove who they are (Week 1) and how services talk in a cluster (Week 5). Now: how does a service prove who it is?
  • A service account is an account for software, not a person. Example: the orders service has an account that may read the orders database.
  • Secrets are things like API keys, passwords and certificates that software uses. Long-lived secrets are risky: if one leaks, it works until someone notices.
  • If a secret is committed to git, treat it as leaked: revoke and replace it first, then remove it from history. GitHub’s secret scanning alerts on many key types.
  • Short-lived credentials are better: a role gives a workload a token that expires in minutes, so a leak is far less harmful.
  • Workload identity gives each workload a verifiable identity without shared secrets. SPIFFE is the standard: a SPIFFE ID is a name like spiffe://shop.example/orders, and an SVID is the document that proves it.
  • Design questions: Who owns this key? When was it last used? What can it reach? What breaks if I revoke it? Most products cannot answer these yet.

Key terms

non-human identityAn identity used by software, such as a service account or API key.
service accountAn account for a program or service, not a person.
secretA key, password or certificate that software uses to authenticate.
API keyA long string an app sends to prove it may use an API.
short-lived credentialA credential that expires quickly, often in minutes or hours.
workload identityA verifiable identity for software, without shared secrets.
SPIFFE IDA standard name for a workload, such as spiffe://shop.example/orders.
SVIDThe document, such as a certificate, that proves a workload’s SPIFFE ID.

What a good answer looks like

  • If one leaks, it keeps working until someone notices and replaces it, which can take months. It often has broad access and no clear owner.
  • Revoke and replace the secret immediately, because it must be treated as compromised. Then remove it from the code and history, and check logs for misuse.
  • A SPIFFE ID is a standard name for a workload, such as spiffe://shop.example/orders. An SVID is the verifiable document, usually a short-lived certificate or token, that proves the workload holds that ID.
