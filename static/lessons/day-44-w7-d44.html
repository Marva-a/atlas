Compliance and policy as code, in plain words

Day 44 · Week 7 · Advanced · about 120 min

Compliance frameworks like SOC 2 and ISO 27001 ask companies to prove they control access and changes, and policy as code keeps those rules in files that are reviewed, tested and versioned like software.

By the end, you can: Distinguish a SOC 2 report (an attestation) from ISO 27001 certification, and explain how policy-as-code differs from a full GitOps pipeline.

Why it matters to a designer

Compliance is why many companies buy security products, and policy as code is how technical teams want to manage them. A designer who can bridge the auditor’s need for evidence and the engineer’s need for git workflows can design features that sell and that people actually use.

Key ideas

  • SOC 2 is a report from an independent auditor that a company’s controls work: who has access, how changes are approved, how incidents are handled. Customers ask suppliers for it before buying.
  • Type 1 checks that controls are designed well at one point in time; Type 2 checks they actually worked over months. SOC 2 itself is an attestation: an auditor's report on how well your controls work, not a pass/fail certification. ISO 27001 is different in kind: it is a certification against an international standard, issued after an accredited audit.
  • Auditors ask for evidence: screenshots, exports and logs that prove each control. Products that make evidence easy to export save customers weeks.
  • Policy as code: rules live in text files in git. Every change is a pull request that someone reviews, tests run automatically, and you can see history and roll back.
  • GitOps means git is the source of truth: when a change is merged, a pipeline applies it automatically. Tailscale supports this for its policy file.
  • Open Policy Agent (OPA) and Cedar (Week 3) are both policy-as-code engines, but they are not interchangeable: each has its own policy language and evaluation model, so a policy written for one cannot simply be dropped into the other.
  • The design challenge: some admins edit in the console, some in git. Products must keep both consistent and show clearly which one is in charge.

Key terms

SOC 2An independent audit report on a company’s security controls.
ISO 27001An international standard for managing information security.
controlA practice or rule that reduces risk, such as requiring approval for changes.
evidenceProof that a control works: logs, exports, screenshots.
policy as codeKeeping rules in versioned files that are reviewed and tested like software.
pull requestA proposed change in git that others review before it is merged.
GitOpsUsing git as the source of truth, with changes applied automatically after merge.
OPAOpen Policy Agent: a widely used policy-as-code engine.

  • What is the difference between SOC 2 Type 1 and Type 2?
  • What are three benefits of policy as code?
  • Why must a product show clearly whether a policy is managed in git or in the console?

What a good answer looks like

  • Type 1 checks that controls are well designed at one moment. Type 2 checks that they actually operated over a period, usually several months.
  • Every change is reviewed in a pull request, tests run before it goes live, and there is a full history with easy rollback.
  • Otherwise an admin edits in the console and the next git sync silently overwrites the change, or the two drift apart. Clear ownership prevents confusion and lost changes.
