Excessive agency and tool permissions

Pathway: AI Security · Lesson 4 · Advanced · about 95 min

An agent becomes dangerous when it has more tools, broader permissions or more autonomy than its task needs, so each tool must be scoped, each consequential action confirmed in context, and human oversight treated as one control, not the security boundary.

By the end, you can: Audit an agent's tools for excessive functionality, permissions and autonomy, propose least-privilege scopes for each, decide which actions need confirmation, and explain why a human approval step cannot be the only safeguard.

Why it matters to a designer

Agent permission screens, tool connection flows and approval prompts are new interfaces with no settled patterns yet. They are where an agent's authority is granted and checked. Designing them well, without causing approval fatigue, is one of the clearest opportunities for a security product designer right now.

Key ideas

  • Day 51 introduced excessive agency. OWASP splits it into three forms: excessive functionality (tools the task does not need, such as a 'run any shell command' tool), excessive permissions (a tool that can write when it only needs to read) and excessive autonomy (consequential actions with no check).
  • Least privilege for tools: give each tool the narrowest operation and data scope. 'Read this user's calendar' rather than 'full Google account'; 'create a draft' rather than 'send email'; 'search tickets in project X' rather than 'admin API'.
  • Act with the user's delegated authority, not more (Day 51): the agent should get scoped, short-lived tokens for each service, issued for that agent, and never a broader service account than the user has. Watch for the confused deputy: a tool with broad rights acting for a user with narrow ones.
  • Confirmation in context: before an irreversible or high-impact action, show what will happen in plain terms (recipient, amount, which records, which permission change), from data the system computed, not just the model's summary of it.
  • Human oversight is a control, not the boundary. People approve quickly when prompts are frequent (approval fatigue, from Day 51), and a convincing model summary can hide a harmful action. Hard limits (rate limits, spending caps, allow-lists, blocked operations) must hold even when a person clicks approve.
  • Agents connecting to tools through MCP need consent per tool and per scope, tokens issued for the right server, and clear warnings when a tool server is new or its description changes.
  • Make authority visible and revocable: a page listing every agent, what it can reach, who granted it, when it last acted and a single place to revoke it. This is Day 50's machine-identity inventory, applied to agents.

Key terms

tool scopeThe exact operations and data a tool is allowed to use.
confused deputyA program with broad rights tricked into using them for someone who should not have that power.
hard limitA rule the system enforces regardless of approvals, such as a spending cap or a blocked action.
allow-listA list of the only things permitted, such as approved recipients or tool servers.
consent screenThe screen where a person grants an app or agent access to their data or tools.

Check yourself

  • What are the three forms of excessive agency? Give an example of each.
  • Why is a human approval step not enough on its own to keep an agent safe?
  • What should a confirmation screen show before an agent issues a refund?

What a good answer looks like

  • Excessive functionality: an email assistant that also has a 'delete mailbox' tool. Excessive permissions: a tool with write access to the whole CRM when it only reads one account. Excessive autonomy: an agent that issues refunds without any check.
  • Because people approve quickly when prompts are frequent, and a persuasive summary from the model may hide what really happens. Hard limits such as caps, allow-lists and blocked actions must still apply even after someone approves.
  • The customer, the order, the exact amount and currency, the reason given, where the money goes, whether it can be reversed, and that these details come from the order system rather than from the model's own wording.
