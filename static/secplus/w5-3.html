Change management and its effect on security

Lesson 19 · Week 5 · Domain 1: General Security Concepts · Objective 1.2 · Beginner · about 120 min

Open this lesson in Atlas →

Professional relevance for cross-functional work

1. Learn the concept

By the end, you can

  • Follow a change from request to documentation.
  • Identify the security impact of a technical change.
  • Choose between backing out and failing forward.

Why it exists and what problem it solves

Unplanned changes cause outages and open security gaps. Many incidents begin with an undocumented firewall exception or a rushed update. Good change management turns risky work into controlled work.

In plain language

Think of road works. Someone asks permission, planners check what roads will be affected, and they set a time when traffic is light. They also plan what to do if it goes wrong, then update the maps when it is finished. Change management applies the same discipline to technology.

2. Technical deep dive

In the business process, an owner is accountable for the change. Stakeholders are the people affected. An impact analysis estimates what could go wrong, including security effects. Test results show that the change worked in a safe environment. A Change Advisory Board (CAB) reviews significant changes through an approval process. Standard operating procedures (SOPs) describe how routine work is done.

A maintenance window is a period agreed in advance when work can happen with minimal disruption. Backout planning is the prepared way to return to the earlier state. Fail forward is the alternative: when going back is riskier or impossible, you fix the problem and keep moving ahead, such as after a database migration that cannot be cleanly reversed.

Technical implications include: changing allow lists or deny lists, so that a new application is not blocked or a dangerous one permitted; restricted activities, meaning actions that are prohibited during the work; downtime; a service restart or application restart; legacy applications, which may break under new settings; and dependencies, where changing one component affects another.

After the change, documentation must catch up: updating diagrams and updating policies and procedures. Version control tracks each revision of code, configurations and documents so that you can see who changed what and return to a previous state.

Walkthrough: Take a firewall rule through change management

  1. The application owner requests a new rule allowing database access from one subnet.
  2. The security team analyzes the impact and checks for a narrower alternative.
  3. The rule is tested in staging, and the test results are attached.
  4. The CAB approves it for Saturday's maintenance window, with a backout plan to remove the rule.
  5. The engineer implements it, checks that it works and updates the network diagram and version-controlled configuration.

Hands-on lab

Write a change request

About 35 min. Text editor, and git in your lab VM

  1. Write a change request to enable a host firewall on your VM. Include owner, stakeholders, impact, test plan, window and backout plan.
  2. In your VM, install git and run git init in a new folder.
  3. Save your firewall settings to a text file, then commit it with git add and git commit.
  4. Change the file, commit again, and use git log and git diff to see what changed.

Expected: A complete change record, and a repository that shows two versions and exactly what differed.

Version control gives you a tamper-evident history and an easy route back, which is why it applies to configurations as well as to code.

Done when:

  • Your request includes all listed elements, including a backout plan.
  • git log shows two commits.

3. See it in real products

Change management reaches design when a change to product settings can lock everyone out. Maintenance windows, previews of impact and rollback controls are all change management expressed in an interface.

In security operations

  • A firewall upgrade needs a service restart, so the team schedules it in a maintenance window, and prepares to restore the old configuration if VPN users cannot connect.
  • Stronger TLS settings break a legacy application. Because dependencies were not analyzed beforehand, the application fails during peak hours.

5. Test your understanding

A. Security+ technical assessment

Exam-style scenario: An update has been applied to a database and has already converted records to a new format. A bug appears, but reverting would lose an hour of transactions. What approach best applies?

Compare your reasoning

Fail forward. Reverting would cause data loss, so the better path is a fix that moves forward, provided that the risk is understood and approved. Normally, the backout plan would be used, but here going back would be more damaging.

1. What is the main purpose of a backout plan?

  • To return to the earlier state if a change fails
  • To decide who approves a change
  • To record the change in the diagram
  • To schedule the work
Answer and explanation
  • Correct: To return to the earlier state if a change fails. It is the prepared route back.
  • Incorrect: To decide who approves a change. Approval is handled by the CAB and approval process.
  • Incorrect: To record the change in the diagram. That is documentation.
  • Incorrect: To schedule the work. Scheduling is the role of the maintenance window.

2. A team wants to deploy an urgent patch that needs a service restart during business hours, and it has not been reviewed. What should happen first in a mature organization?

  • It follows the emergency change route with an owner, impact analysis and approval
  • The patch is deployed immediately, and no record is needed
  • The firewall is disabled for the update
  • The system is decommissioned
Answer and explanation
  • Correct: It follows the emergency change route with an owner, impact analysis and approval. Urgency changes the speed, and the discipline should remain.
  • Incorrect: The patch is deployed immediately, and no record is needed. Skipping records is how undocumented risk builds up.
  • Incorrect: The firewall is disabled for the update. This creates additional exposure.
  • Incorrect: The system is decommissioned. This is out of proportion to the situation.

3. After TLS settings are hardened on a server, an old reporting tool stops connecting. What did the change process most likely miss?

  • Identifying dependencies and legacy applications
  • A CAB meeting agenda
  • Reducing the maintenance window
  • Enabling more deny lists
Answer and explanation
  • Correct: Identifying dependencies and legacy applications. The impact analysis should have found this reliance on older settings.
  • Incorrect: A CAB meeting agenda. An agenda would not reveal the technical dependency.
  • Incorrect: Reducing the maintenance window. Timing did not cause the incompatibility.
  • Incorrect: Enabling more deny lists. A deny list is unrelated.

4. Put these steps in order.

Correct order
  1. Request the change and assign an owner
  2. Analyze the impact
  3. Test and collect results
  4. Obtain CAB approval
  5. Implement during the maintenance window
  6. Update diagrams and procedures

Each step uses the output of the one before, and documentation closes the change.

5. A company uses application allow listing. A new version of an approved application is deployed by hash, and it now fails to run. What change was missed?

  • Updating the allow list to include the new version
  • Restarting the DNS service
  • Changing the network diagram
  • Removing the backout plan
Answer and explanation
  • Correct: Updating the allow list to include the new version. The new version has a new hash, which is not yet on the list.
  • Incorrect: Restarting the DNS service. DNS does not determine whether an application is allowed to run.
  • Incorrect: Changing the network diagram. Diagrams document systems but do not affect execution.
  • Incorrect: Removing the backout plan. This would only remove a safety net.

6. Review and references

Common mistakes

  • Treating documentation as optional cleanup. Out-of-date diagrams mislead responders during an incident.
  • Always assuming a change can be reversed. Some cannot, and that should be identified before you start.

Summary

  • Changes need an owner, an impact analysis, testing and approval.
  • Plan a backout or a fail-forward approach before starting.
  • Updated documentation and version control keep records true.
