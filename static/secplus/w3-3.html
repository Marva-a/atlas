Application protocols: HTTP, TLS, SSH, FTP and VPN

Lesson 11 · Week 3 · Foundations · Foundation (not an exam objective) · Beginner · about 120 min

Open this lesson in Atlas →

Professional relevance for cross-functional work

1. Learn the concept

By the end, you can

  • Describe what happens when a browser loads an HTTPS page.
  • Choose secure protocols over their insecure equivalents.
  • Explain what a VPN does and what it does not do.

Why it exists and what problem it solves

Many breaches trace back to a protocol sending secrets in clear text, or to a false sense of safety from a padlock or a VPN. Knowing what each protocol really protects helps you choose correctly.

In plain language

HTTP is like sending a postcard: anyone handling it can read it. HTTPS is the same conversation in a locked box that only you and the website can open. A VPN is a private tunnel through a public road, between you and the VPN's far end. Beyond that exit, the traffic is on open road again.

The padlock in a browser means the connection to that site is encrypted and the certificate checks out. It does not mean the website is honest. Criminals can get certificates too.

2. Technical deep dive

The Hypertext Transfer Protocol (HTTP) defines requests and responses using methods such as GET and POST, and status codes such as 200, 404 and 500. HTTPS is HTTP inside Transport Layer Security (TLS). TLS provides encryption, integrity checking and server authentication using certificates. In a TLS handshake, the client and server agree on parameters, the server presents a certificate, and they derive shared session keys.

Secure Shell (SSH) provides an encrypted remote shell, usually on port 22. File Transfer Protocol (FTP) sends data and credentials unencrypted. SFTP runs over SSH and is different from FTPS, which is FTP with TLS. DNS and DHCP, seen earlier, normally operate without encryption, although encrypted DNS options exist.

A virtual private network (VPN) creates an encrypted tunnel between two points. A remote-access VPN connects a user to an organization, and a site-to-site VPN joins two networks. Common technologies are TLS-based VPNs and IPsec. A full-tunnel VPN sends all traffic through the tunnel, while a split-tunnel VPN sends only some traffic through it.

The certificate proves which server this is. The key exchange gives both sides the same session keys without sending them.

Full tunnel: the company sees and protects everything, at the cost of speed. Split tunnel: faster, but the direct traffic is not inspected.

Walkthrough: What happens when you open https://example.com

  1. DNS resolves the name to an address.
  2. Your browser opens a TCP connection to port 443.
  3. The TLS handshake runs. The server presents its certificate, and the browser checks it.
  4. Both sides derive session keys, and encryption begins.
  5. The browser sends an HTTP GET request inside TLS, and the server responds.

Hands-on lab

Inspect a TLS certificate

About 30 min. Any browser, optional OpenSSL

  1. Open a major website that uses HTTPS, click the icon beside the address and view the certificate.
  2. Note the domain it was issued to, the issuer and the validity dates.
  3. Optional: run openssl s_client -connect example.com:443 -servername example.com and find the certificate chain and TLS version.
  4. Visit an http:// version of a site if one exists and note the browser's warning.

Expected: The certificate names the site, an issuing certificate authority and a limited validity period.

The browser trusts the site because a chain of signatures leads to an authority it already trusts. That proves the name matches the key, not that the business is trustworthy.

Done when:

  • You recorded the subject, issuer and expiry date.
  • You can state one thing the padlock does prove and one it does not.

3. See it in real products

HTTP status codes and TLS shape everyday product behaviour. A 401 means the system does not know who you are, a 403 means it knows and refuses, and a certificate error stops the user before your product can even speak. Each deserves different words and a different next step.

In security operations

  • A login page served over HTTP sends the password as readable text across every network on its path.
  • A staff member on a split-tunnel VPN has corporate traffic protected, but personal browsing goes directly out and bypasses corporate filtering.

5. Test your understanding

A. Security+ technical assessment

Exam-style scenario: An administrator proposes using Telnet for router management, because the management network is internal. What is the risk, and what should be used instead?

Compare your reasoning

Telnet sends credentials and commands in clear text, so anyone able to capture traffic on that network could read them. Internal does not mean safe. Use SSH, which encrypts the session.

1. Which protocol is the secure replacement for Telnet?

  • SSH
  • HTTP
  • FTP
  • SNMPv1
Answer and explanation
  • Correct: SSH. SSH encrypts remote administration sessions.
  • Incorrect: HTTP. HTTP is a web protocol and is not encrypted.
  • Incorrect: FTP. FTP is file transfer and is not encrypted.
  • Incorrect: SNMPv1. SNMPv1 is a monitoring protocol and is not encrypted.

2. What does a valid HTTPS connection prove?

  • The connection is encrypted and the server holds a certificate valid for that name
  • The website is honest and safe to give your data to
  • The website has no vulnerabilities
  • Nobody can ever attack your account
Answer and explanation
  • Correct: The connection is encrypted and the server holds a certificate valid for that name. TLS gives encryption and verifies the server's identity by name.
  • Incorrect: The website is honest and safe to give your data to. Scam sites can obtain valid certificates.
  • Incorrect: The website has no vulnerabilities. TLS protects the connection, not the site's code.
  • Incorrect: Nobody can ever attack your account. TLS addresses only the connection.

3. A vendor says it supports SFTP. What does that mean?

  • File transfer runs over SSH
  • FTP runs over TLS
  • FTP runs without encryption
  • HTTP runs on port 21
Answer and explanation
  • Correct: File transfer runs over SSH. SFTP is the SSH File Transfer Protocol.
  • Incorrect: FTP runs over TLS. That describes FTPS.
  • Incorrect: FTP runs without encryption. That is plain FTP.
  • Incorrect: HTTP runs on port 21. This describes neither.

4. True or false: a VPN protects a website from attacks launched by a logged-in user.

  • True
  • False
Answer and explanation
  • Incorrect: True. A VPN encrypts the path. It does not judge what the user does.
  • Correct: False. A VPN protects data in transit through the tunnel, and does not stop malicious actions at the destination.

6. Review and references

Common mistakes

  • Treating the padlock as proof that a site is legitimate.
  • Confusing SFTP with FTPS. SFTP runs over SSH on port 22, while FTPS adds TLS to FTP.

Summary

  • HTTPS is HTTP inside TLS.
  • Replace clear-text protocols with their secure versions.
  • A VPN protects the path it covers and nothing beyond it.
