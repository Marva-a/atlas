Vulnerability management tasks

Lesson 42 · Week 11 · Domain 4: Security Operations · Objective 4.3 · Intermediate · about 120 min

Open this lesson in Atlas →

Direct product design relevance

1. Learn the concept

By the end, you can

  • Run a vulnerability management cycle.
  • Use identification methods including scanning and CSPM.
  • Verify and report on remediation.

Why it exists and what problem it solves

New flaws appear daily, so this is continuous work. Exam scenarios ask what to do next: scan, prioritize, fix, verify or report.

In plain language

Vulnerability management is like regular building maintenance. You inspect, decide what is urgent, fix it, check the fix and keep records.

2. Technical deep dive

Identification methods include scanning with vulnerability tools; Internet Protocol Address Management (IPAM), which tracks address use and can reveal unknown hosts; cloud security posture management (CSPM), which finds cloud misconfigurations; and source code review. Credentialed scans sign in for more accurate results, and non-credentialed scans show what an outsider would see.

Prioritization uses severity assessment plus context, and penetration test report review, which shows what was actually exploitable. Remediation may mean patching, changing configuration, applying a compensating control or formally accepting the risk. Verification confirms the fix, usually by rescanning.

Reporting can be internal, to management and asset owners, or external. External routes include a bounty program, which pays researchers for valid findings, and responsible disclosure policies, which tell researchers how to report safely. A false positive is a reported problem that does not exist. A false negative is a real problem that was missed.

Walkthrough: Handle one scan finding

  1. Confirm it is real, and rule out a false positive.
  2. Check exposure, exploitation status and asset importance.
  3. Assign an owner and a due date.
  4. Apply the fix under change management.
  5. Rescan to verify, then close and report.

Hands-on lab

Scan only your own VM

About 40 min. nmap in your lab VM, against localhost only

  1. Install nmap with sudo apt install nmap.
  2. Start a test service, such as sudo apt install openssh-server.
  3. Run nmap -sV 127.0.0.1 and record the open ports and versions.
  4. Disable the service with sudo systemctl stop ssh and rescan to verify.
  5. Write a three-line finding: issue, priority and action. Do not scan any other system.

Expected: The port appears, then disappears after the fix.

Rescanning proves the result. A ticket being closed proves nothing on its own.

Done when:

  • You recorded a finding before and after.
  • You wrote a three-line report.

3. See it in real products

Vulnerability dashboards often list thousands of findings sorted by severity, leaving teams unable to act. What helps is context: is the system exposed, is the flaw being exploited in the wild, and who owns it? Exceptions need a design too, because accepted risk should not disappear from view.

In security operations

  • CSPM reports a storage bucket that became publicly readable last night, and it is closed before any data is taken.
  • After a patch, a rescan still flags the server. The team finds that the service was never restarted, so the fix was not active.

4. Apply it as a Product Designer

Design brief: Design a vulnerability prioritization view

About 45 min

Scenario: A security platform shows a customer 4,000 open findings. Teams ignore it because everything appears critical.

Problem statement: Findings are sorted only by CVSS severity, so the list doesn't reveal what needs attention first or who should act.

Your design task:

  • Define the fields a person needs in order to make a triage decision.
  • Design the prioritized list and the detail view.
  • Design the exception flow: accept, defer or mark as a false positive.
  • Design verification after a fix.

Technical security constraints:

  • CVSS measures severity, and it does not account for your specific environment by itself.
  • Risk exceptions need an owner, a reason and an expiry date.
  • A finding is resolved only when a rescan confirms it.

User needs:

  • Engineers need to see what to fix and how.
  • Security leads need to see trends and overdue items.
  • Auditors need evidence of exceptions.

Expected deliverable: A list and detail design, an exception flow and a defined priority model.

Evaluation criteria:

  • Priority combines severity with exposure, exploitation and asset value.
  • Exceptions expire, and accepted risk stays visible.
  • The first screen makes the next action clear.
  • The priority model is presented as an input for security to validate.

Senior-level considerations:

  • Prioritization logic is a security decision, and your role is making that logic understandable.
  • Watch for metrics that reward closing tickets instead of reducing risk.

A design review is not a security sign-off. Have security engineers confirm technical decisions.

Questions a Senior Product Designer should ask

Engineering:

  • How are duplicate findings merged, and how accurate is ownership?

Security:

  • Which inputs set our priority: CVSS, known exploitation or asset criticality?

Product:

  • What decision should a person be able to make within a minute?

5. Test your understanding

A. Security+ technical assessment

Exam-style scenario: A patch was deployed and the ticket closed, but the next scan still lists the vulnerability. What step was skipped, and what should happen?

Compare your reasoning

Verification was skipped. The team should find out whether the patch failed, the service needs a restart or the result is a false positive, then rescan.

1. Put these in order.

Correct order
  1. Identify vulnerabilities
  2. Prioritize by severity and context
  3. Remediate
  4. Verify the fix
  5. Report the outcome

A fix cannot be verified until it has been made, and reporting should reflect the verified state.

2. A scanner reports a flaw that does not exist on the system. What is this?

  • A false positive
  • A false negative
  • A zero-day
  • A compensating control
Answer and explanation
  • Correct: A false positive. The alert is incorrect.
  • Incorrect: A false negative. That is a missed real flaw.
  • Incorrect: A zero-day. That is a flaw with no fix.
  • Incorrect: A compensating control. This is an alternative protection.

3. Which tool is designed to find misconfigured cloud resources?

  • CSPM
  • IPAM
  • UPS
  • HIDS
Answer and explanation
  • Correct: CSPM. It continually assesses cloud configuration.
  • Incorrect: IPAM. This tracks IP addresses.
  • Incorrect: UPS. This is power protection.
  • Incorrect: HIDS. This watches a single host.

4. A company wants outside researchers to know how to report flaws safely. What should it publish?

  • A responsible disclosure policy
  • A DMARC record
  • A risk register
  • A CRL
Answer and explanation
  • Correct: A responsible disclosure policy. It explains how and where to report.
  • Incorrect: A DMARC record. This is for email.
  • Incorrect: A risk register. This is an internal record.
  • Incorrect: A CRL. This is for certificates.

5. Which scan generally gives the most accurate view of missing patches on a host?

  • Credentialed
  • Non-credentialed
  • Passive DNS lookup
  • A ping sweep
Answer and explanation
  • Correct: Credentialed. It signs in and inspects the system.
  • Incorrect: Non-credentialed. This gives only an outside view.
  • Incorrect: Passive DNS lookup. This does not check software.
  • Incorrect: A ping sweep. This only finds live hosts.

Rate your work in the interactive app, where it counts toward design competency only.

1. Which finding usually deserves attention first?

  • A medium finding on an exposed system under active attack
  • A critical finding on an isolated, decommissioned test machine
  • The oldest finding in the list, whatever it happens to affect
  • The finding with the longest technical description available
Answer and explanation
  • Correct: A medium finding on an exposed system under active attack. Real exploitation and exposure raise the actual risk.
  • Incorrect: A critical finding on an isolated, decommissioned test machine. The score is high, but the exposure and impact are low.
  • Incorrect: The oldest finding in the list, whatever it happens to affect. Age alone doesn't measure risk.
  • Incorrect: The finding with the longest technical description available. Description length says nothing about risk.

6. Review and references

Common mistakes

  • Closing a ticket without rescanning.
  • Treating every scanner finding as confirmed.

Summary

  • Identify, prioritize, remediate, verify, report.
  • Use context, not just severity.
  • Provide a safe way for outsiders to report flaws.
