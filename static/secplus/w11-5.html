OAuth 2.0 and OpenID Connect in depth

Lesson 46 · Week 11 · Domain 4: Security Operations · Objective 4.5 · Intermediate · about 90 min

Open this lesson in Atlas →

Direct product design relevance

1. Learn the concept

By the end, you can

  • Name the four OAuth roles and what each one does.
  • Follow the Authorization Code flow with PKCE step by step.
  • Explain access tokens, refresh tokens, scopes, expiry and revocation.
  • Decide when OIDC, Authorization Code, Client Credentials or the Device flow fits.

Why it exists and what problem it solves

Almost every modern product connects to other products. OAuth decides how much access those connections receive and how that access ends, so misunderstanding it leads to over-granted, long-lived access that nobody can see.

In plain language

Imagine lending a parking valet a key that starts the car but cannot open the boot, and that stops working at midnight. You never hand over your own key. OAuth works like that: an app receives a limited, expiring pass instead of your password. OpenID Connect adds a signed note saying who you are.

2. Technical deep dive

OAuth 2.0 defines four roles. The resource owner is usually the user. The client is the application that wants access. The authorization server authenticates the user, records consent and issues tokens. The resource server is the API holding the data, and it accepts or rejects tokens. Scopes name what the client may do, such as reading a calendar, and the granted scopes can be narrower than those requested.

In the Authorization Code flow the client sends the browser to the authorization server. The user signs in and approves the request. The browser returns to a pre-registered redirect URI with a short-lived, single-use code. The client then exchanges that code at the token endpoint, over a back channel, for tokens. Exact matching of the redirect URI stops an attacker from sending the code somewhere else.

Proof Key for Code Exchange (PKCE) protects that code. The client creates a random code verifier, sends a SHA-256 hash of it as the code challenge at the start, and reveals the verifier only when exchanging the code. An attacker who steals the code cannot produce the verifier. The current OAuth security best practice, RFC 9700, requires protection against code injection and recommends PKCE for all clients, including ones with a secret. It also says the Implicit grant should not be used and the Resource Owner Password Credentials grant must not be used.

An access token is presented to the resource server and should be short-lived and narrowly scoped. A refresh token lets the client get a new access token without asking the user again, is sent only to the authorization server, and should be rotated or sender-constrained for public clients. Expiry is automatic. Revocation ends access early, as RFC 7009 describes. A self-contained JSON Web Token (JWT) access token can often keep working until it expires, even after revocation, unless the resource server checks with the authorization server. That is one reason lifetimes are kept short.

The Client Credentials grant is for one service talking to another with no user present. The Device Authorization grant suits input-limited devices such as televisions. OpenID Connect adds authentication on top of OAuth: requesting the openid scope returns an ID token, a signed JWT intended for the client, that states who authenticated. An ID token should not be sent to APIs, and an access token should not be treated as proof of who signed in.

PKCE ties the code to the app that started the flow. Only that app knows the secret behind the hash it sent at the start.

Walkthrough: Follow Authorization Code with PKCE

  1. The client creates a random code verifier and hashes it to make a code challenge.
  2. The client redirects the browser to the authorization server with its client ID, redirect URI, scopes, state value and code challenge.
  3. The user signs in and approves the scopes.
  4. The authorization server redirects back to the registered URI with a single-use code.
  5. The client checks the state value, then posts the code and the original verifier to the token endpoint.
  6. The authorization server hashes the verifier, compares it with the challenge and issues tokens.
  7. The client calls the resource server with the access token.

Hands-on lab

Compute a PKCE challenge and read a JWT, offline

About 25 min. openssl and base64 in your lab VM, using no real tokens

  1. In your VM, set the published test verifier from RFC 7636 Appendix B: V=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
  2. Run: printf %s "$V" | openssl dgst -sha256 -binary | base64 | tr '+/' '-_' | tr -d '='
  3. Compare the output with the RFC's expected challenge, E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
  4. Make a harmless token payload: printf '{"sub":"lab-user","scope":"calendar.read","exp":1893456000}' | base64 and then decode it again with base64 -d. Note that anyone can read an encoded payload.
  5. Write one sentence on why encoding is not encryption. Use only sample values, and never paste a real token into any tool.

Expected: Your computed challenge matches the RFC value exactly, and the decoded payload shows the sample claims.

PKCE works because a hash cannot be reversed to reveal the verifier. JWT payloads are signed, usually not encrypted, so they must not hold secrets.

Done when:

  • Your challenge matches the published value.
  • You can explain why a stolen code alone is useless when PKCE is used.

3. See it in real products

The consent screen is where a person grants another product access to their work, often without reading it. Scope names written for developers, such as files.readwrite.all, mean little to the person approving them. The experience also continues long after consent: tokens expire, integrations break, and administrators need a way to see and end access.

In security operations

  • A project tool asks to read a user's calendar. The consent page lists calendar read only, and the tool never sees the user's password.
  • An administrator revokes a reporting integration. New refresh attempts fail at once, and any JWT access token already issued stops working when it expires unless the API checks revocation.

4. Apply it as a Product Designer

Design brief: Design a third-party integration and consent experience

About 60 min

Scenario: You are designing a B2B SaaS application. A customer wants to connect its workspace to an external analytics platform that requests access to projects and user activity.

Problem statement: The current flow shows a raw list of scopes and an Allow button. Once connected, integrations are invisible, and nobody knows what they can reach.

Your design task:

  • Design the connection flow from starting in your product through consent and back.
  • Write the permission and consent screen, with plain-language scope explanations.
  • Design token expiration and reconnection states.
  • Design the integrations list, including what each one can access and last used.
  • Design revocation, including what happens to the integration's data.

Technical security constraints:

  • Authorization Code with PKCE is the expected flow, and the product never sees the other service's password.
  • Requested scopes should be the minimum needed, and the granted scopes may be narrower.
  • Revocation may not stop existing access tokens until they expire.

User needs:

  • Users need to understand what they are granting.
  • Workspace administrators need to approve, review and revoke integrations.
  • Integration builders need to know why they were refused a scope.

Expected deliverable: A connection flow, consent screen, reconnection states and an integrations management screen.

Evaluation criteria:

  • The design reflects the real OAuth flow, including expiry, refresh and revocation.
  • Excessive scopes, a malicious consent request and an offboarded installer are addressed.
  • A person can say in plain words what the integration will be able to do.
  • The design covers the full life of an integration, including who owns it when its installer leaves.

Senior-level considerations:

  • Ask what happens when the person who connected an integration leaves the company, since its access may depend on their account.
  • Be accurate about revocation timing, because "access removed immediately" may not be true.

A design review is not a security sign-off. Have security engineers confirm technical decisions.

Questions a Senior Product Designer should ask

Engineering:

  • Which scopes do we support, and can they be split further?
  • How quickly does revocation take effect, given our token lifetimes?

Security:

  • Which scopes need administrator approval?

Product:

  • What happens to the customer's workflow when an integration disconnects?

5. Test your understanding

A. Security+ technical assessment

Exam-style scenario: A single-page app needs to read a user's documents through an API on that user's behalf. A developer suggests collecting the user's password and sending it to the API. What should be used instead?

Compare your reasoning

The Authorization Code flow with PKCE and a narrow read scope. The app never handles the password, access is limited and expiring, and the user or an administrator can revoke it. The password grant must not be used.

1. In OAuth 2.0, which component accepts or rejects access tokens when an API is called?

  • The resource server
  • The authorization server
  • The client
  • The resource owner
Answer and explanation
  • Correct: The resource server. It hosts the API and checks each token presented.
  • Incorrect: The authorization server. It issues tokens, but the API call goes elsewhere.
  • Incorrect: The client. It presents tokens and does not judge them.
  • Incorrect: The resource owner. The owner grants consent and does not check tokens.

2. What does PKCE specifically protect against?

  • Use of a stolen authorization code
  • A weak user password
  • A forged TLS certificate
  • A user approving too many scopes
Answer and explanation
  • Correct: Use of a stolen authorization code. The thief cannot supply the original code verifier.
  • Incorrect: A weak user password. PKCE does not change password strength.
  • Incorrect: A forged TLS certificate. Certificate validation handles this.
  • Incorrect: A user approving too many scopes. Consent design and policy handle this.

3. Where should a client send a refresh token?

  • Only to the authorization server
  • To every API it calls
  • To the resource owner's browser storage for sharing
  • To the identity of the next client
Answer and explanation
  • Correct: Only to the authorization server. It is exchanged there for new access tokens.
  • Incorrect: To every API it calls. This exposes a powerful credential widely.
  • Incorrect: To the resource owner's browser storage for sharing. This would increase exposure.
  • Incorrect: To the identity of the next client. Tokens are not passed between clients.

4. An administrator revokes an integration, but its self-contained JWT access token still works for ten more minutes. What explains this?

  • The API validates the JWT locally until it expires
  • Revocation always requires a server restart
  • The refresh token has become an ID token
  • OAuth does not support revocation at all
Answer and explanation
  • Correct: The API validates the JWT locally until it expires. Local validation does not consult revocation state.
  • Incorrect: Revocation always requires a server restart. Restarting is not part of revocation.
  • Incorrect: The refresh token has become an ID token. Tokens do not change type.
  • Incorrect: OAuth does not support revocation at all. RFC 7009 defines token revocation.

5. Match each situation to the best OAuth choice.

Correct matches
  • A nightly job calls an API as itself: Client Credentials
  • A mobile app acts for a signed-in user: Authorization Code with PKCE
  • A television shows a code to enter on a phone: Device Authorization

Ask who is acting, and whether that party can use a browser and hold a secret.

6. True or false: an ID token should be sent to an API as proof of access.

  • True
  • False
Answer and explanation
  • Incorrect: True. APIs should receive access tokens.
  • Correct: False. An ID token is intended for the client and describes authentication.

B. Product design assessment

Rate your work in the interactive app, where it counts toward design competency only.

1. An analytics app needs to read project names, yet it asks for full read and write on all workspace data. What should the product support?

  • Clear scopes, with admins able to refuse excess requests
  • Approving automatically if the app comes from a known company
  • Hiding detailed scopes so that the consent screen looks simpler
  • Granting everything now and asking the vendor to reduce it later
Answer and explanation
  • Correct: Clear scopes, with admins able to refuse excess requests. Visibility and admin control encourage least privilege before access is granted.
  • Incorrect: Approving automatically if the app comes from a known company. A familiar name doesn't justify write access that it doesn't need.
  • Incorrect: Hiding detailed scopes so that the consent screen looks simpler. Simplicity that hides the grant defeats the purpose of consent.
  • Incorrect: Granting everything now and asking the vendor to reduce it later. Access has already been over-granted by the time anyone asks.

6. Review and references

Common mistakes

  • Treating a successful OAuth grant as proof of who the user is. Use OIDC for sign-in.
  • Assuming revocation stops every token instantly.
  • Asking for broad scopes up front because it is easier than asking later.

Summary

  • OAuth delegates limited, expiring access without sharing passwords.
  • Authorization Code with PKCE is the normal choice when a user is present.
  • Access tokens go to APIs, refresh tokens go to the authorization server, and ID tokens go to the client.
