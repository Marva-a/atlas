Clients, servers and the parts of an application

Lesson 3 · Week 1 · Foundations · Foundation (not an exam objective) · Beginner · about 120 min

Open this lesson in Atlas →

Direct product design relevance

1. Learn the concept

By the end, you can

  • Explain the client-server model and what a server does.
  • Separate a web server, an application server and a database by their roles.
  • Identify the trust boundaries in a basic three-tier web application.

Why it exists and what problem it solves

Most attacks cross a boundary between a client and a server. Knowing which part talks to which part tells you where to place a firewall, where to validate input, and what is exposed to the entire internet.

In plain language

A restaurant is a good model. You are the client, and you ask for something. The waiter takes your order to the kitchen, and the kitchen gets ingredients from the storeroom. You never walk into the storeroom yourself. In a web application, your browser is the customer, the web server is the waiter, the application server is the kitchen, and the database is the storeroom.

A server is not a special kind of magic box. It is a computer, physical or virtual, running software that waits for requests and answers them. Your own laptop could be a server if it ran that software.

2. Technical deep dive

In the client-server model, the client starts a request and the server responds. A web server such as nginx or Microsoft IIS receives HTTP requests and returns pages. An application server runs business logic, such as checking whether a payment is allowed. A database stores structured data and answers queries, often written in Structured Query Language (SQL).

Splitting these into tiers means each tier can be protected separately. The web tier faces the internet, the application tier accepts traffic only from the web tier, and the database accepts traffic only from the application tier. An API, or application programming interface, is a defined way for one program to ask another for data or an action.

A trust boundary is any line where data moves between parts that trust each other differently. Data arriving from a client is untrusted, because the person controlling the client can change anything in it.

Each tier talks only to its neighbour. Data from the browser crosses a trust boundary.

Key terms

ClientThe device or program that makes a request.
ServerA computer or program that listens for requests and answers them.
Web serverSoftware that receives web requests and returns responses.
Application serverSoftware that runs an application's business logic.
DatabaseAn organized store of data that answers queries.
SQLStructured Query Language, used to read and change data in many databases.
APIApplication programming interface: a defined way for programs to talk to each other.
TierA separate layer of an application, such as web, application or database.
Trust boundaryA point where data passes between parts with different levels of trust.

Walkthrough: Follow one login through three tiers

  1. Your browser sends your username and password to the web server over an encrypted connection.
  2. The web server passes the request to the application server.
  3. The application server asks the database for the stored password record for that username.
  4. The database returns the record, and the application compares it with what you sent.
  5. The application tells the browser whether the login worked, and the database was never exposed to you.

Hands-on lab

See client and server in your browser

About 30 min. Any desktop browser's developer tools

  1. Open a website you use, then press F12 (or Cmd+Option+I on a Mac) and choose the Network tab.
  2. Reload the page and click the first entry in the list.
  3. Find the request URL, the method (usually GET) and the status code (200 means OK).
  4. Look at the Response Headers and find one named Server, if the site provides it.
  5. Draw the page load as: browser, then web server, then whatever you think is behind it. Mark the trust boundary.

Expected: You saw individual requests from your browser and responses from a server, each with a status code.

Your browser is only one side of the conversation. You can inspect and even change everything on your side, which is why servers must never trust a client's input.

Done when:

  • You recorded a request URL, method and status code.
  • You drew at least one trust boundary and can say why it is there.

3. See it in real products

A single screen in a business app is usually several systems working together: the browser renders it, an API checks who you are and what you may see, a database returns records, and a third party may supply avatars or analytics. Security decisions live at each of those boundaries, and the screen is only where they become visible.

A loading spinner, a partial table or a "you do not have access" message is often the visible result of one of those parts failing or refusing. Designers who can see the parts write far better states and far better questions.

In security operations

  • Online banking: your browser requests a balance, the web tier passes it on, the application tier checks that the account is yours and the database returns the figure. The database is never directly reachable from the internet.
  • A phone app is also a client. It calls the same kind of API as a website, which is why the server must check permissions rather than trusting the app.

4. Apply it as a Product Designer

Design brief: Map one screen to the system behind it

About 45 min

Scenario: You have joined a team building a customer-records screen for a B2B SaaS product. Engineering says the page "calls three services", and nobody on the design team knows what that means for the experience.

Problem statement: The design covers the happy path only. No one has mapped which part of the system supplies each piece of the screen, so failure and permission states are missing.

Your design task:

  • Choose a real screen from a product you can freely use, or sketch a customer-records screen.
  • Annotate each region with what supplies it: client, API, database or third party.
  • Mark one trust boundary, where data crosses from one party's control to another's.
  • Design the state shown when one region fails while the others succeed.

Technical security constraints:

  • The browser is under the user's control, so nothing shown or hidden there can enforce access by itself.
  • The API must check identity and permission on every request.
  • Data sent to a third party leaves your organization's direct control.

User needs:

  • Support staff need to tell a permissions problem apart from an outage.
  • Customers need to keep working when one non-critical region fails.

Expected deliverable: An annotated screen with a labelled system map, one marked trust boundary and one partial-failure state.

Evaluation criteria:

  • The map correctly places enforcement on the server and not in the interface.
  • At least one trust boundary and one sensitive data item are identified.
  • The partial-failure state tells users what still works and what to do next.
  • The annotation is clear enough to start a useful conversation with an engineer.

Senior-level considerations:

  • A designer's system map is a conversation starter, and an engineer must confirm it before anyone relies on it.
  • Ask which failures are worth designing for separately, because a dedicated state for every error creates cost with little benefit.

A design review is not a security sign-off. Have security engineers confirm technical decisions.

Questions a Senior Product Designer should ask

Engineering:

  • Which requests does this screen make, and which of them can fail on their own?
  • Where is the permission check actually enforced: the client, the API or both?

Security:

  • Which data on this screen is most sensitive, and does any of it reach a third party?

Product:

  • Which of these failures would a customer notice first, and what would they need to do next?

5. Test your understanding

A. Security+ technical assessment

Exam-style scenario: A shop's website checks the price of an item in the browser and sends the total to the server, which charges whatever total it receives. What is the design flaw?

Compare your reasoning

The server trusts data from the client. Anyone can alter a request from their own browser and send a lower total. The server must calculate the price itself from its own data, because the client is on the untrusted side of the boundary.

1. In the client-server model, which side normally starts the conversation?

  • The client
  • The server
  • The database
  • The switch
Answer and explanation
  • Correct: The client. The client makes the request and the server listens and answers.
  • Incorrect: The server. A server waits for requests rather than starting them.
  • Incorrect: The database. A database answers queries from an application.
  • Incorrect: The switch. A switch forwards traffic and does not take part in the application.

2. In a three-tier application, which placement is most appropriate for the database?

  • Reachable only from the application tier
  • Reachable directly from the internet
  • Reachable from every user's browser
  • On the same public address as the website
Answer and explanation
  • Correct: Reachable only from the application tier. Limiting access to the tier that needs it reduces exposure.
  • Incorrect: Reachable directly from the internet. Direct exposure is the opposite of the three-tier design.
  • Incorrect: Reachable from every user's browser. Browsers should never query the database directly.
  • Incorrect: On the same public address as the website. Sharing the public address would expose it unnecessarily.

3. Match each part to the restaurant role it resembles.

Correct matches
  • Browser: Customer placing an order
  • Web server: Waiter taking the order
  • Application server: Kitchen preparing the meal
  • Database: Storeroom of ingredients

The analogy shows that each part only talks to its neighbours, which is how the tiers are protected in practice.

4. True or false: data sent from a client can be trusted if the website's own JavaScript created it.

  • True
  • False
Answer and explanation
  • Incorrect: True. The person using the browser controls that JavaScript and can change or replace what is sent.
  • Correct: False. Anything arriving from the client can be altered, so the server must validate it.

B. Product design assessment

Rate your work in the interactive app, where it counts toward design competency only.

1. A designer hides the "Delete" button from viewers and notes "security handled". What is the main problem?

  • The API may accept the delete with no permission check
  • Hidden buttons always make pages load more slowly
  • Viewers need the button visible so they can request access
  • Delete actions cannot ever be hidden from any kind of user
Answer and explanation
  • Correct: The API may accept the delete with no permission check. Hiding a control changes the interface only, so the server must enforce access.
  • Incorrect: Hidden buttons always make pages load more slowly. Performance is not the concern raised by this note.
  • Incorrect: Viewers need the button visible so they can request access. That may be a usability question, but it does not address enforcement.
  • Incorrect: Delete actions cannot ever be hidden from any kind of user. Hiding is a valid design choice when it is paired with enforcement.

6. Review and references

Common mistakes

  • Believing a check in the browser is a security control. It improves usability, but only checks on the server can be relied on.
  • Thinking a server must be special hardware. A server is defined by the role software plays.

Summary

  • A client asks and a server answers.
  • Web, application and database tiers can be separated and protected individually.
  • Data from the client crosses a trust boundary and must be validated by the server.
