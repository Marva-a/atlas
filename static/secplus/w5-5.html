Public key infrastructure and certificates

Lesson 21 · Week 5 · Domain 1: General Security Concepts · Objective 1.3 · Intermediate · about 120 min

Open this lesson in Atlas →

Professional relevance for cross-functional work

1. Learn the concept

By the end, you can

  • Explain how a certificate chain is validated.
  • Compare CRL and OCSP, and self-signed and third-party certificates.
  • Generate a certificate signing request.

Why it exists and what problem it solves

Certificates are how you know you are talking to your real bank and not an impostor. When a certificate expires or a key is stolen, services go down or trust breaks. PKI failures are a common cause of outages as well as attacks.

In plain language

A certificate is an ID card for a website or person. A certificate authority is the government office that issues it. You trust the ID because you trust the office. Public key infrastructure is the whole system of offices, ID cards and lists of cancelled cards.

2. Technical deep dive

Public key infrastructure (PKI) is the set of people, policies and systems that create, manage and revoke certificates. A certificate binds a public key to an identity and is signed by a certificate authority (CA). The private key stays secret with the owner. The public key may be shared. Key escrow means a trusted third party holds a copy of a key so that it can be recovered, for example if an employee leaves or loses it. Escrowed keys need strict controls.

A root of trust is the starting point that is trusted by default. Browsers and operating systems ship with root CA certificates. A root CA usually signs an intermediate CA, and the intermediate CA signs end-entity certificates. To validate, the client checks the chain up to a trusted root, the name, the validity dates and the revocation status.

To request a certificate, you generate a key pair and create a certificate signing request (CSR), which contains the public key and identifying details. The CA verifies the request and returns a signed certificate. The private key is never sent. A wildcard certificate covers all first-level subdomains of a domain, such as *.example.com. A Subject Alternative Name (SAN) lists additional names. A third-party certificate comes from a public CA and is broadly trusted. A self-signed certificate is signed by its own key, and clients will not trust it automatically, so it suits internal testing.

Revocation is used when a certificate must be withdrawn early, for example because its key was stolen. A certificate revocation list (CRL) is a signed list of revoked serial numbers that a client downloads. The Online Certificate Status Protocol (OCSP) lets a client ask about one certificate in real time. OCSP stapling lets the server attach a recent signed OCSP response.

A chain of trust. The browser trusts the root, so it can verify what the root vouches for.

Walkthrough: How your browser trusts a site

  1. The server sends its certificate and any intermediate certificates.
  2. The browser checks that the name matches the address and that the certificate is within its dates.
  3. It verifies each signature up the chain until it reaches a root it already trusts.
  4. It checks revocation status using OCSP or CRL data.
  5. If all pass, the handshake continues. If not, you see a warning.

Hands-on lab

Create a CSR and read a chain

About 40 min. OpenSSL in your lab VM, and a browser

  1. Run openssl req -new -newkey rsa:2048 -nodes -keyout lab.key -out lab.csr and enter example lab values.
  2. Run openssl req -in lab.csr -noout -text and find the public key and subject.
  3. Make a self-signed certificate: openssl x509 -req -in lab.csr -signkey lab.key -days 30 -out lab.crt.
  4. Run openssl x509 -in lab.crt -noout -issuer -subject -dates and note that issuer and subject match.
  5. In a browser, view a major site's certificate chain and identify its root and intermediate.

Expected: The CSR shows the details without the private key. The issuer and subject of your self-signed certificate match. The public site shows a chain of two or more.

Matching issuer and subject is the mark of self-signing. A public site's chain reaches a root already in your browser, so it is trusted automatically.

Done when:

  • You generated a CSR and inspected it.
  • You identified the root and intermediate of a real site.

3. See it in real products

Certificates become visible when one expires and a customer's integration stops working without warning. Products that manage certificates for customers need expiry warnings, clear ownership and recovery instructions.

In security operations

  • A website's certificate expires over a weekend, so browsers warn all visitors and sales stop. Many organizations now automate renewal.
  • A company runs an internal CA and installs its root on company devices, so that internal sites are trusted without a public CA.

5. Test your understanding

A. Security+ technical assessment

Exam-style scenario: A web server's private key is stolen, but its certificate has 200 days of validity remaining. What should be done, and how will clients learn of it?

Compare your reasoning

Revoke the certificate, generate a new key pair and CSR, and install a new certificate. Clients learn through OCSP or by receiving an updated CRL. Simply replacing the certificate is not enough, because the attacker could still present the old one with the stolen key.

1. What is a CRL?

  • A published list of revoked certificates
  • A request sent to get a new certificate
  • A chip that stores keys
  • A type of symmetric key
Answer and explanation
  • Correct: A published list of revoked certificates. A CRL names certificates that should no longer be trusted.
  • Incorrect: A request sent to get a new certificate. That is a CSR.
  • Incorrect: A chip that stores keys. That describes a TPM.
  • Incorrect: A type of symmetric key. A CRL is not a key.

2. What does a CSR contain?

  • The public key and identifying information
  • The private key and a password
  • A list of revoked certificates
  • The CA's root private key
Answer and explanation
  • Correct: The public key and identifying information. The CA signs these after verification.
  • Incorrect: The private key and a password. The private key must never leave its owner.
  • Incorrect: A list of revoked certificates. That is a CRL.
  • Incorrect: The CA's root private key. Nobody outside the CA should ever have this.

3. A certificate for *.example.com is valid for which name?

  • mail.example.com
  • a.b.example.com
  • example.org
  • mail.example.net
Answer and explanation
  • Correct: mail.example.com. A wildcard covers one level of subdomain.
  • Incorrect: a.b.example.com. A wildcard does not normally cover multiple subdomain levels.
  • Incorrect: example.org. This is a different domain.
  • Incorrect: mail.example.net. This is a different domain.

4. Why would an organization use key escrow?

  • To recover encrypted data if a key is lost or its holder leaves
  • To replace the need for certificates
  • To speed up TLS handshakes
  • To publish private keys so anyone can verify signatures
Answer and explanation
  • Correct: To recover encrypted data if a key is lost or its holder leaves. A controlled copy of the key permits recovery.
  • Incorrect: To replace the need for certificates. Escrow is about storing keys and does not replace certificates.
  • Incorrect: To speed up TLS handshakes. Escrow is unrelated to speed.
  • Incorrect: To publish private keys so anyone can verify signatures. Private keys must not be published.

5. Put these certificate steps in order.

Correct order
  1. Generate a key pair
  2. Create a CSR
  3. CA verifies and signs the certificate
  4. Install the certificate on the server
  5. Revoke if the key is compromised

The key pair must exist first. The CSR carries the public key to the CA, and revocation is a later safeguard.

6. Review and references

Common mistakes

  • Thinking a CSR contains the private key. It contains only the public key and identity details.
  • Assuming that when a certificate is replaced, it no longer matters. A compromised certificate should also be revoked.

Summary

  • PKI binds public keys to identities through trusted CAs.
  • Clients validate the chain, name, dates and revocation.
  • CRLs are downloaded lists, and OCSP is a real-time lookup.

Flashcards

What is the difference between CRL and OCSP?

A CRL is a downloaded list, and OCSP is a real-time query about one certificate.

Is a private key included in a CSR?

No. A CSR contains the public key and identity details.
