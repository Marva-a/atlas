Application, email and deception controls

Lesson 40 · Week 10 · Domain 4: Security Operations · Objective 4.1 · Intermediate · about 120 min

Open this lesson in Atlas →

Direct product design relevance

1. Learn the concept

By the end, you can

  • Apply application security controls.
  • Explain how SPF, DKIM, DMARC and BIMI work together.
  • Choose deception technologies.

Why it exists and what problem it solves

Web applications and email are the two most common ways into an organization. Deception gives defenders a rare advantage, since nobody legitimate should touch a decoy.

In plain language

Input validation is like checking that a phone number field has only digits before accepting it. SPF is a list of who may send mail for your domain, DKIM is a wax seal on the letter, and DMARC tells recipients what to do if either one fails. A honeypot is a decoy safe left out to catch thieves.

2. Technical deep dive

Application security covers input validation, which checks data against what is expected; secure cookies, using the Secure, HttpOnly and SameSite attributes; static code analysis, which reviews source code without running it; and code signing, which proves who published code and that it has not been altered. Repositories should use secrets scanning to find leaked credentials.

Email security uses DNS records. Sender Policy Framework (SPF) lists the servers allowed to send for a domain. DomainKeys Identified Mail (DKIM) adds a digital signature to messages. Domain-based Message Authentication, Reporting, and Conformance (DMARC) tells recipients how to handle messages failing checks, such as none, quarantine or reject, and asks for reports. Brand Indicators for Message Identification (BIMI) displays a verified brand logo, and depends on DMARC enforcement.

Deception and disruption technology includes a honeypot (a decoy system), a honeynet (a network of decoys), a honeyfile (a decoy document), a honeytoken (fake data or a credential that raises an alert when used) and a canary account (a decoy account that should never be used). Any use of these indicates something is wrong, so false positives are low.

SPF is the guest list, DKIM is the wax seal, and DMARC is the domain owner's rule for what to do when either one fails.

Walkthrough: Read a domain's email security

  1. Look up the SPF TXT record, starting v=spf1.
  2. Look up the DMARC record at _dmarc.domain.
  3. Check the DMARC policy: p=none only monitors, while p=reject is enforcing.
  4. Check whether messages carry a DKIM-Signature header.

Hands-on lab

Inspect email authentication

About 35 min. nslookup, and your own mail client

  1. Run nslookup -type=txt followed by a large public domain, and find an SPF record.
  2. Run nslookup -type=txt _dmarc.domain for the same domain, and note its policy.
  3. In your own mailbox, open a message's full headers and find the Authentication-Results line.
  4. Note whether SPF, DKIM and DMARC passed.

Expected: An SPF record, a DMARC policy and pass or fail results in a real message.

These results are what mail systems use to decide on spoofed messages.

Done when:

  • You identified an SPF record and a DMARC policy.
  • You read SPF and DKIM results in a header.

3. See it in real products

Sending email from a customer's own domain requires SPF, DKIM and DMARC records, which is a difficult task to hand to a marketing manager. Products that handle this well turn a technical protocol into a guided, verifiable setup, and they say plainly what is at risk if it stays incomplete.

In security operations

  • A domain publishes a DMARC policy of reject, so forged mail claiming to be from the domain is refused by receiving servers.
  • A fake credentials file on a file share triggers an alert the moment anyone opens it.

4. Apply it as a Product Designer

Design brief: Design an email authentication setup wizard

About 45 min

Scenario: An email marketing product lets customers send from their own domain. Many customers skip authentication, and their mail ends up in spam or can be spoofed.

Problem statement: The current settings page lists DNS records with no explanation, and the person using it is often not the person who controls DNS.

Your design task:

  • Explain SPF, DKIM and DMARC in plain language within the flow.
  • Design the setup with a hand-off to a DNS administrator.
  • Design verification, propagation wait, partial success and failure states.
  • Show the path from a monitoring DMARC policy to enforcement.

Technical security constraints:

  • DNS changes can take time to propagate and the product cannot speed them up.
  • Moving to a reject policy too early can block legitimate mail.
  • Records must be copied exactly, so manual retyping should be avoided.

User needs:

  • Marketers need to know what to ask for, and from whom.
  • DNS administrators need exact values with no marketing context.
  • Account owners need to see the risk of leaving setup unfinished.

Expected deliverable: A setup wizard flow, a hand-off page and a state list covering verification.

Evaluation criteria:

  • The flow represents SPF, DKIM and DMARC correctly and in the right order.
  • The design explains the harm of spoofing and of an early reject policy.
  • A non-technical user can complete their part and hand off the rest.
  • The design defines success in terms of authenticated mail, and not of completed screens.

Senior-level considerations:

  • A setup step that depends on another team needs a designed hand-off, because the product loses the user at that point.
  • Confirm the recommended policy timing with deliverability experts.

A design review is not a security sign-off. Have security engineers confirm technical decisions.

Questions a Senior Product Designer should ask

Engineering:

  • How do we check the records, and how often?
  • What happens to mail while the setup is incomplete?

Security:

  • What is the recommended DMARC policy progression for customers?

Product:

  • Who at a customer usually has access to DNS?

5. Test your understanding

A. Security+ technical assessment

Exam-style scenario: Attackers keep spoofing a company's domain in phishing emails to its customers. Which control lets the company instruct receiving servers to reject those messages?

Compare your reasoning

DMARC with a policy of reject, supported by correctly configured SPF and DKIM.

1. Which record lists mail servers authorized for a domain?

  • SPF
  • BIMI
  • OCSP
  • SNMP
Answer and explanation
  • Correct: SPF. It is published in DNS.
  • Incorrect: BIMI. BIMI displays logos.
  • Incorrect: OCSP. This is for certificates.
  • Incorrect: SNMP. This is for monitoring.

2. What does a DMARC policy of p=reject do?

  • It asks receiving servers to refuse messages that fail authentication
  • It encrypts all outgoing mail
  • It displays the company logo
  • It disables spam filtering
Answer and explanation
  • Correct: It asks receiving servers to refuse messages that fail authentication. This is the strongest policy setting.
  • Incorrect: It encrypts all outgoing mail. DMARC does not encrypt mail.
  • Incorrect: It displays the company logo. That is BIMI.
  • Incorrect: It disables spam filtering. It does not.

3. A fake administrator account exists and is never used legitimately. An alert fires when someone tries it. What is this?

  • A canary account
  • A gMSA
  • An emergency access account
  • A captive portal
Answer and explanation
  • Correct: A canary account. Any use is suspicious.
  • Incorrect: A gMSA. That is a real service account.
  • Incorrect: An emergency access account. That is real and has a legitimate use.
  • Incorrect: A captive portal. This is a guest network page.

4. Which cookie attribute stops page scripts from reading a cookie?

  • HttpOnly
  • Secure
  • Domain
  • Max-Age
Answer and explanation
  • Correct: HttpOnly. JavaScript cannot access HttpOnly cookies.
  • Incorrect: Secure. This limits cookies to HTTPS.
  • Incorrect: Domain. This limits where cookies are sent.
  • Incorrect: Max-Age. This controls lifetime.

5. Match each need to a control.

Correct matches
  • Prove a software update came from the publisher: Code signing
  • Find flaws in source without running it: Static code analysis
  • Find cloud keys in a code base: Secrets scanning
  • Reject letters in a numeric field: Input validation

Each one addresses a different stage of building and shipping software.

B. Product design assessment

Rate your work in the interactive app, where it counts toward design competency only.

1. Which step should a setup wizard recommend first for a domain with an unknown sending landscape?

  • Start DMARC in monitoring mode and review reports
  • Publish DMARC with an immediate reject policy today
  • Remove all SPF records before adding any DKIM keys
  • Wait until spoofing has been reported by customers
Answer and explanation
  • Correct: Start DMARC in monitoring mode and review reports. This reveals legitimate senders before anything is blocked.
  • Incorrect: Publish DMARC with an immediate reject policy today. Legitimate mail from unknown senders could be blocked.
  • Incorrect: Remove all SPF records before adding any DKIM keys. This removes existing protection and breaks authentication.
  • Incorrect: Wait until spoofing has been reported by customers. Waiting leaves the domain exposed and gives no data.

6. Review and references

Common mistakes

  • Assuming SPF alone stops spoofing. SPF checks the envelope, and DMARC adds alignment and policy.
  • Thinking p=none protects. It only monitors.

Summary

  • Validate input and sign code.
  • SPF, DKIM and DMARC work together.
  • Decoys produce high-confidence alerts.
