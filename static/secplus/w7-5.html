Credentials in memory: local accounts, credential dumping, pass-the-hash and memory leaks

Lesson 31 · Week 7 · Domain 2: Threats, Vulnerabilities, and Attacks · Objective 2.5, 2.4 · Advanced · about 110 min

Open this lesson in Atlas →

Professional relevance for cross-functional work

1. Learn the concept

By the end, you can

  • Explain local authentication and how it differs from a central directory.
  • Describe credential dumping and pass-the-hash, and why a stolen hash can be as useful as a password.
  • Distinguish a memory leak from memory disclosure and from a buffer overflow.
  • Name the controls that limit credential theft and lateral movement.

Why it exists and what problem it solves

The last lesson covered attacks that guess or trick their way to a password. This one covers what happens after an attacker gets onto one machine: they look for credentials already sitting in memory or on disk, and reuse them to move to the next machine without ever learning a password. It explains why breaches spread so quickly through some networks, and why advice such as unique local administrator passwords matters.

In plain language

A password hash should be like a fingerprint of a key: useful for checking, useless for opening the door. Pass-the-hash works where a door accepts the fingerprint itself. Credential dumping is a thief photographing every fingerprint left on the counter. Shared local administrator passwords are one master key cut for every office: steal it once, open them all. A memory leak is a tap left running: nothing is stolen, but eventually the room floods.

2. Technical deep dive

Local authentication checks credentials stored on the device itself. Windows keeps local account password hashes in the Security Account Manager (SAM) database. Linux keeps them in /etc/shadow, salted and computed with slow algorithms such as yescrypt or SHA-512 crypt, marked by prefixes such as $y$ and $6$. A central directory, such as Active Directory or another LDAP directory, holds one account that works across many systems and can be disabled in one place. Local accounts are useful when the network is down, but they are often forgotten, rarely reviewed and sometimes share one password across many machines.

Credential dumping is extracting stored credentials from an operating system: from the memory of the process that handles sign-ins (on Windows, the Local Security Authority Subsystem Service, LSASS), from the SAM database, or from a domain controller's directory database. It usually needs administrator rights, so it typically follows privilege escalation. MITRE ATT&CK lists it as OS Credential Dumping (T1003).

Pass-the-hash reuses a stolen password hash to authenticate, without cracking it. It works against NTLM, an older Windows authentication protocol in which the client proves it knows the hash, not the password itself. Windows NT hashes are not salted, so the same password produces the same hash on every machine: if many computers share one local administrator password, one dumped hash unlocks all of them. Moving from machine to machine this way is called lateral movement. A similar attack against Kerberos reuses stolen tickets and is called pass-the-ticket. ATT&CK lists pass-the-hash as T1550.002.

Controls: give every machine a unique, regularly rotated local administrator password (Windows LAPS automates this); never sign in to ordinary workstations with domain administrator accounts; use dedicated privileged access workstations; isolate stored secrets with features such as Credential Guard, which uses virtualization-based security; restrict or disable NTLM where it is not needed; and alert on access to LSASS memory and on unusual network logons. In Windows logs, an event 4624 with logon type 3 using NTLM from an unexpected machine is a common lead.

A memory leak is a software flaw in which a program keeps memory it no longer needs, so its memory use grows until the system slows down or the program crashes. It is an availability problem: an attacker who can trigger the leak repeatedly can cause a denial of service. Memory disclosure is different: a flaw lets someone read memory they should not, which can expose secrets such as keys or session tokens. A buffer overflow writes past the end of a memory area and can corrupt data or run code.

Walkthrough: Investigate suspected credential theft on Windows

  1. Start from the first compromised machine and the time of the first alert.
  2. Look for processes that opened LSASS memory, usually reported by endpoint detection and response.
  3. Search for network logons, event 4624 with logon type 3, from that machine to others shortly afterwards.
  4. Note whether NTLM was used and which accounts signed in, especially local administrator accounts.
  5. Treat every machine reached as compromised, and every credential used on them as exposed.
  6. Reset affected passwords, rotate local administrator passwords and revoke sessions and tickets.

Hands-on lab

Salted hashes and a memory leak

About 35 min. Linux lab VM with sudo

  1. In your lab VM, create two test users with the same password: sudo useradd -m labuser1 and sudo useradd -m labuser2, then echo 'labuser1:Spring2026!' | sudo chpasswd and the same for labuser2.
  2. Run: sudo grep labuser /etc/shadow. Compare the two hash fields and note the algorithm prefix, such as $y$ or $6$.
  3. In one terminal run: python3 -c "import time; k=[]; [(k.append(bytearray(5_000_000)), time.sleep(0.5)) for _ in range(20)]". In a second terminal, run ps -o rss,cmd -C python3 a few times while it runs.
  4. Delete the test users: sudo userdel -r labuser1 and sudo userdel -r labuser2.

Expected: The two hashes are completely different despite the same password, and the Python process's memory (RSS) grows steadily by about 5 MB each half second until it ends.

A unique salt per user means a stolen hash cannot be matched to other accounts or reused across machines. Unsalted NT hashes are identical wherever the password is the same, which is what makes pass-the-hash spread. The script never releases what it allocates, the defining behaviour of a memory leak.

Done when:

  • You explained why the two hashes differ.
  • You observed memory growing and named the impact of a real leak as availability.

3. See it in real products

Credential theft and lateral movement show up in products as admin consoles: where local administrator passwords are rotated, where privileged sign-ins are reviewed and where sessions are revoked after a compromise. Products that run on customers' machines also decide what credentials they leave behind in memory and on disk.

In security operations

  • After phishing one employee, an attacker gains administrator rights on that laptop and dumps the local administrator's NT hash. Every laptop in the company was built from the same image with the same local administrator password, so the hash signs in to all of them over the network.
  • A web service's memory use climbs steadily after each malformed request and the service crashes every few hours. That is a memory leak being triggered, which is a denial-of-service risk rather than a data leak.

4. Apply it as a Product Designer

No design exercise here, on purpose. The account compromise investigation exercise in Week 12 applies this: tracing where stolen credentials were used and recovering every affected account.

Questions a Senior Product Designer should ask

Engineering:

  • Does our software store or cache credentials on devices, and could a local administrator extract them?

Security:

  • Which of our features would help an attacker move from one compromised machine to others?

Product:

  • When a customer finds a compromised machine, can they see which accounts signed in to it and revoke them?

5. Test your understanding

A. Security+ technical assessment

Exam-style scenario: Within an hour of one laptop being compromised, alerts show the same local Administrator account signing in over the network to forty other laptops using NTLM. No passwords were changed and no one reported a phishing email after the first. What is the likely technique, why did it spread so far, and what should change?

Compare your reasoning

Credential dumping on the first laptop followed by pass-the-hash: the attacker reused the local Administrator NT hash without cracking it. It spread because every laptop shared the same local administrator password, so the same hash worked everywhere. Contain the laptops, rotate every local administrator password, deploy unique rotated passwords with LAPS, restrict NTLM, and alert on LSASS access and unusual network logons.

1. An attacker authenticates to file servers using a dumped NT hash, without knowing the password. What is this?

  • Pass-the-hash
  • Password spraying
  • Credential stuffing
  • Brute force
Answer and explanation
  • Correct: Pass-the-hash. The hash itself is accepted as proof under NTLM.
  • Incorrect: Password spraying. That tries common passwords against many accounts.
  • Incorrect: Credential stuffing. That reuses usernames and passwords leaked from other sites.
  • Incorrect: Brute force. That guesses many passwords against one account.

2. Why does one dumped local administrator hash often unlock many Windows machines?

  • Machines built from one image often share the same local administrator password, and NT hashes are not salted
  • NTLM encrypts the hash with each machine's public key
  • Kerberos tickets never expire
  • The SAM database is shared across the network
Answer and explanation
  • Correct: Machines built from one image often share the same local administrator password, and NT hashes are not salted. The same password gives the same hash everywhere.
  • Incorrect: NTLM encrypts the hash with each machine's public key. It does not; the hash is the proof.
  • Incorrect: Kerberos tickets never expire. Tickets expire, and this attack does not use them.
  • Incorrect: The SAM database is shared across the network. Each machine has its own SAM.

3. Which control most directly stops one stolen local administrator hash from working on other machines?

  • A unique, rotated local administrator password on every machine
  • A longer screen-lock timeout
  • A web application firewall
  • DNSSEC
Answer and explanation
  • Correct: A unique, rotated local administrator password on every machine. Each machine's hash is then different.
  • Incorrect: A longer screen-lock timeout. This does not affect stored hashes.
  • Incorrect: A web application firewall. This filters web traffic.
  • Incorrect: DNSSEC. This protects DNS answers.

4. A service slowly uses more memory with each request until it crashes. What flaw is this?

  • A memory leak
  • Memory disclosure
  • A race condition
  • Directory traversal
Answer and explanation
  • Correct: A memory leak. Memory is never released, so use grows until failure.
  • Incorrect: Memory disclosure. Nothing is being read that should not be.
  • Incorrect: A race condition. That depends on timing between operations.
  • Incorrect: Directory traversal. That uses path sequences to reach files.

5. Match each stolen item to the attack that reuses it.

Correct matches
  • A Kerberos ticket: Pass-the-ticket
  • An NT password hash: Pass-the-hash
  • A session cookie: Session hijacking
  • Passwords from another site's breach: Credential stuffing

Ask what was stolen, then where it can be presented as proof.

6. Put the stages of this common attack in order.

Correct order
  1. Phishing gives the attacker a foothold on one workstation
  2. Privilege escalation gives administrator rights on it
  3. Credential dumping extracts hashes from memory
  4. Pass-the-hash is used for lateral movement to other machines

Dumping usually needs administrator rights, and stolen hashes are then reused to move further.

6. Review and references

Common mistakes

  • Thinking a hash is safe because it cannot be reversed. Under NTLM the hash itself is enough to authenticate.
  • Calling a memory leak a data leak. A memory leak exhausts resources; memory disclosure exposes data.

Summary

  • Credentials stored on a device can be dumped by anyone who gains administrator rights on it.
  • Pass-the-hash reuses a hash without cracking it; shared local passwords let it spread.
  • Unique local passwords, isolated secrets, restricted NTLM and monitoring limit the damage.
