Identity: accounts, federation, SSO, SAML, LDAP, OAuth and OIDC

Lesson 44 · Week 11 · Domain 4: Security Operations · Objective 4.5 · Intermediate · about 120 min

Open this lesson in Atlas →

Direct product design relevance

1. Learn the concept

By the end, you can

  • Manage accounts from provisioning through deprovisioning.
  • Explain federation and single sign-on.
  • Clearly distinguish SAML, LDAP, OAuth and OpenID Connect.

Why it exists and what problem it solves

Identity is now the main security boundary, and stolen or over-privileged accounts are behind many breaches. The difference between OAuth and OIDC trips up even experienced people.

In plain language

Federation is like using your passport in another country: a government you trust vouches for you. Single sign-on is a wristband at a festival: show it once and you can enter each stage.

OAuth is a hotel key card: it says what doors you can open, not who you are. OpenID Connect adds a photo ID on top: it tells the application who you are.

2. Technical deep dive

Provisioning creates accounts and grants access. Deprovisioning removes them, and should happen promptly when someone leaves. Permissions assignments have implications: granting a permission to a group affects everyone in it. Identity proofing verifies a person is who they claim to be before issuing credentials. Federation allows trust between organizations, so that a person can use one identity across them.

Single sign-on (SSO) lets a user authenticate once for many applications. Security Assertions Markup Language (SAML) exchanges XML assertions between an identity provider and a service provider, and is common in enterprise SSO. Lightweight Directory Access Protocol (LDAP) queries and manages directory information such as users and groups. Open Authorization (OAuth) is an authorization framework: it grants an application limited access to resources on a user's behalf using access tokens. OAuth by itself does not tell an application who the user is.

OpenID Connect (OIDC) is an identity layer built on OAuth 2.0. It adds an ID token, a signed statement about who authenticated. Use OIDC to sign users in, and OAuth to grant access to an API. OIDC does not appear in the current exam list by name, but it is essential to understanding OAuth correctly.

Account types include user accounts; privileged accounts, either global (rights across an environment) or local (rights on one system); service accounts for applications; third-party accounts for outside organizations; and emergency access accounts, sometimes called break-glass accounts, which are tightly controlled, used only in emergencies and closely monitored.

OAuth answers what an app may access. OpenID Connect adds who the user is.

Single sign-on: authenticate once, and the identity provider vouches for you to every app. Federation extends that trust to other organizations.

Walkthrough: Decide which standard is in use

  1. An app needs to read a user's files on another service. That is OAuth.
  2. A website needs to know who has signed in using an outside provider. That is OIDC.
  3. A corporate intranet application accepts XML assertions from an identity provider. That is SAML.
  4. An application looks up a user's group in a directory. That is LDAP.

Hands-on lab

Trace an OIDC sign-in

About 40 min. Browser developer tools, on your own account

  1. Open a site that supports signing in with an account you own. Open the Network tab and preserve the log.
  2. Start signing in and find a request with response_type and scope in the URL.
  3. Note whether scope includes openid, the sign that OIDC is in use.
  4. Note the redirect back to the site. Do not share or paste any tokens or codes anywhere.

Expected: A request that has parameters such as client_id, redirect_uri and scope.

The openid scope signals OIDC, while scopes such as calendar read describe OAuth API access.

Done when:

  • You located the authorization request.
  • You can explain what the openid scope means.

3. See it in real products

Enterprise single sign-on is usually configured by one IT administrator, once, with little margin for error. A wrong setting can lock out an entire company. Certificate rotation, just-in-time accounts and an emergency access route are what separate a professional identity product from a form that accepts a metadata file.

In security operations

  • Sign in with Google uses OIDC to tell a site who you are. Letting an app read your calendar uses OAuth access to an API.
  • An employee leaves and HR's system triggers automatic deprovisioning across all applications via SSO.

4. Apply it as a Product Designer

Design brief: Design enterprise SSO setup

About 60 min

Scenario: A B2B product is adding SAML single sign-on for enterprise customers. An IT administrator must connect the identity provider and then enforce SSO for 2,000 people without locking anyone out.

Problem statement: A one-step "enable SSO" switch can lock out the whole company, including the administrator who enabled it.

Your design task:

  • Design domain verification and connection setup.
  • Design a test-before-enforce stage, with clear success and failure diagnostics.
  • Design a staged rollout and an emergency access path.
  • Design the certificate expiry warning and rotation flow.
  • Decide what happens to existing passwords, sessions and unmatched accounts.

Technical security constraints:

  • Domain ownership must be verified, or someone could claim another company's users.
  • At least one emergency route must survive an identity provider failure.
  • SSO authenticates users, while provisioning and removal need separate handling.

User needs:

  • IT administrators need confidence before enforcement.
  • Employees need the change to be nearly invisible.
  • Security teams need offboarding to work.

Expected deliverable: A setup flow from verification to enforcement, with lockout prevention and diagnostics.

Evaluation criteria:

  • Domain verification and test-before-enforce are both included.
  • Lockout, an expired certificate and a compromised break-glass account are addressed.
  • A SAML failure gives the administrator a specific, actionable cause.
  • Migration of existing accounts and sessions is treated as part of the design.

Senior-level considerations:

  • Enterprise administrators are expert users with high stakes, so show precise technical detail and don't hide it.
  • Include the offboarding story, because sign-in is only half of the identity life cycle.

A design review is not a security sign-off. Have security engineers confirm technical decisions.

Questions a Senior Product Designer should ask

Engineering:

  • Can we test a SAML configuration before enforcing it for everyone?
  • What happens to existing sessions and accounts when SSO is switched on?

Security:

  • How is the break-glass account protected and monitored?

Product:

  • Which identity providers do most customers use?

5. Test your understanding

A. Security+ technical assessment

Exam-style scenario: A mobile app needs permission to post to a user's calendar on another service, and must not see the user's password. Which standard fits?

Compare your reasoning

OAuth 2.0, because it delegates limited access through tokens. If the app also needed to know who the user is, it would use OpenID Connect too.

1. What is OAuth 2.0 primarily for?

  • Delegated authorization
  • Encrypting a hard disk
  • Sending log messages
  • Assigning IP addresses
Answer and explanation
  • Correct: Delegated authorization. It lets an app access resources on a user's behalf.
  • Incorrect: Encrypting a hard disk. This is unrelated.
  • Incorrect: Sending log messages. This is syslog.
  • Incorrect: Assigning IP addresses. This is DHCP.

2. Which token tells an application who authenticated?

  • The ID token from OpenID Connect
  • An OAuth access token
  • A DKIM signature
  • A CRL entry
Answer and explanation
  • Correct: The ID token from OpenID Connect. It carries identity claims.
  • Incorrect: An OAuth access token. Its purpose is resource access.
  • Incorrect: A DKIM signature. This relates to email.
  • Incorrect: A CRL entry. This relates to certificate revocation.

3. Which step is most urgent when an employee is terminated?

  • Disable the employee's accounts and access
  • Update the network diagram
  • Rotate backups
  • Replace the firewall
Answer and explanation
  • Correct: Disable the employee's accounts and access. Prompt deprovisioning prevents continued access.
  • Incorrect: Update the network diagram. It may be needed, but is not urgent.
  • Incorrect: Rotate backups. This is unrelated.
  • Incorrect: Replace the firewall. This is unrelated.

4. How should emergency access accounts be treated?

  • Rarely used, strongly protected and closely monitored
  • Shared widely for convenience
  • Used for daily administration
  • Left without a password
Answer and explanation
  • Correct: Rarely used, strongly protected and closely monitored. They bypass normal controls, so any use must be reviewed.
  • Incorrect: Shared widely for convenience. This defeats accountability.
  • Incorrect: Used for daily administration. This defeats their purpose.
  • Incorrect: Left without a password. This is unsafe.

5. Match each scenario to its standard.

Correct matches
  • XML assertions for enterprise SSO: SAML
  • Directory lookups for users and groups: LDAP
  • Letting an app call an API on your behalf: OAuth
  • Signing in with an outside identity provider: OpenID Connect

Ask whether the purpose is authentication, authorization or directory lookup.

B. Product design assessment

Rate your work in the interactive app, where it counts toward design competency only.

1. An administrator turns on SSO enforcement, and a metadata mistake then blocks all sign-ins. What should have prevented this?

  • A test stage before enforcement and an emergency route
  • A confirmation dialog asking "Are you sure?" before saving
  • A requirement that all administrators use the same browser
  • An automatic email telling employees that SSO has changed
Answer and explanation
  • Correct: A test stage before enforcement and an emergency route. This catches errors before they affect everyone, and it leaves a way back.
  • Incorrect: A confirmation dialog asking "Are you sure?" before saving. Confirmation doesn't reveal whether the configuration really works.
  • Incorrect: A requirement that all administrators use the same browser. The browser has nothing to do with a metadata mistake.
  • Incorrect: An automatic email telling employees that SSO has changed. Announcing the change doesn't stop the lockout.

6. Review and references

Common mistakes

  • Calling OAuth an authentication protocol. It delegates authorization, and OIDC adds authentication.
  • Leaving accounts active after someone leaves.

Summary

  • Manage accounts across their entire life.
  • SSO reduces repeated sign-ins, and federation extends trust.
  • OAuth grants access, and OIDC states who the user is.
