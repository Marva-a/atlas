Protecting data: types, states, classifications and methods

Lesson 34 · Week 9 · Domain 3: Security Architecture · Objective 3.3 · Intermediate · about 120 min

Open this lesson in Atlas →

Direct product design relevance

1. Learn the concept

By the end, you can

  • Identify data types, states and classifications.
  • Pick a protection method to fit the need.
  • Distinguish masking, tokenization and encryption.

Why it exists and what problem it solves

Data is usually what attackers are after. Knowing what you have and what state it is in determines how to protect it.

In plain language

Think of money. In a vault it is at rest. In an armored truck it is in transit. On the counter while a teller counts it, it is in use. Each state needs its own protection.

2. Technical deep dive

Structured data has a defined format, such as database tables. Unstructured data has none, such as documents, images and email. Data at rest is stored. Data in transit moves across a network. Data in use is being processed in memory, which is hardest to protect. Classifications include public, sensitive, confidential, restricted, critical, and in government settings secret and top secret.

Methods: masking hides part of a value, such as showing only the last four digits. Hashing creates a one-way digest. Filtering removes or blocks certain data. Tokenization replaces a sensitive value with a random token, stored in a separate vault. Encryption transforms data so that a key is required. Data transpose rearranges characters or fields, a weak method by itself. De-identification (deidentification) removes information that links data to a person. Obfuscation makes data harder to interpret without strong protection.

Tokenization swaps a sensitive value for a random stand-in. Unlike encryption, there is no key that turns a token back into the value.

Walkthrough: Choose a method

  1. Need to process payments without storing cards? Tokenization.
  2. Need staff to confirm a customer without seeing everything? Masking.
  3. Need to store passwords? Salted hashing.
  4. Need to send a file securely? Encryption.
  5. Need to share data for research? De-identification.

3. See it in real products

Data classification decides what a person sees. Masking shows a card's last four digits, tokenization lets staff work with a stand-in, and reveal-on-demand controls record who viewed a value. The three data states also appear in product questions: is it safe at rest, in transit and on screen while in use?

In security operations

  • A store's point-of-sale system handles tokens, so a breach of that system does not expose actual card numbers.
  • A support agent sees only the last four digits of a card, through masking.

4. Apply it as a Product Designer

Design brief: Design sensitive data display and access

About 60 min

Scenario: Staff at a health insurer use an internal portal showing member records, including government ID numbers, diagnoses and bank details. Today, every staff member sees everything.

Problem statement: Access is all-or-nothing, and there is no record of who viewed which sensitive field.

Your design task:

  • Classify each field on the record and justify each level.
  • Choose masking, tokenization or restricted reveal for each field.
  • Design reveal-with-reason, including the record it creates.
  • Design what appears in exports, printouts, logs and support screenshots.

Technical security constraints:

  • Masking must be applied by the server, so the full value does not reach an unauthorized browser.
  • Hashing can't be reversed, so a value that must be displayed can't be stored only as a hash.
  • Viewing data on screen is the "in use" state, and encryption at rest doesn't protect it.

User needs:

  • Claims staff need full values occasionally, for a defined reason.
  • Members expect their data to be seen only by those who need it.
  • Privacy officers need to audit unusual access.

Expected deliverable: A field classification table, a protection method per field and designs for the reveal flow.

Evaluation criteria:

  • Each protection method is technically appropriate for how that field is used.
  • Exports, logs and screenshots are treated as leak paths.
  • Routine tasks can be finished without revealing unneeded data.
  • Reveal friction is matched to data classification, and it is not the same everywhere.

Senior-level considerations:

  • Masking in the interface alone is decoration, so confirm where the protection is really applied.
  • Classification belongs to the data owner, so use the organization's scheme and do not invent your own.

A design review is not a security sign-off. Have security engineers confirm technical decisions.

Questions a Senior Product Designer should ask

Engineering:

  • Is this field encrypted, hashed, tokenized or masked, and where does that happen?
  • Can a masked value be recovered by an API call that bypasses the interface?

Security:

  • How is this data classified, and which rules follow from that?

Product:

  • Who truly needs to see the full value, and how often?

5. Test your understanding

A. Security+ technical assessment

Exam-style scenario: A retailer wants to keep customer card references for repeat purchases without keeping card numbers on its own systems. Which method fits?

Compare your reasoning

Tokenization. The retailer stores tokens, and the real numbers remain in the payment provider's secure vault.

1. Data stored on a backup drive is in which state?

  • At rest
  • In transit
  • In use
  • Tokenized
Answer and explanation
  • Correct: At rest. It is stored.
  • Incorrect: In transit. It is not moving.
  • Incorrect: In use. It is not being processed.
  • Incorrect: Tokenized. That is a protection method, not a state.

2. Which statement best describes tokenization?

  • A sensitive value is replaced by a random stand-in mapped in a secure vault
  • A value is transformed with a key
  • A value is converted into a one-way digest
  • Only part of a value is displayed
Answer and explanation
  • Correct: A sensitive value is replaced by a random stand-in mapped in a secure vault. The token has no mathematical link to the value.
  • Incorrect: A value is transformed with a key. That is encryption.
  • Incorrect: A value is converted into a one-way digest. That is hashing.
  • Incorrect: Only part of a value is displayed. That is masking.

3. Match each need to a method.

Correct matches
  • Show only the last four digits: Masking
  • Replace a card number with a random value: Tokenization
  • Remove names from a research data set: Deidentification
  • Protect a file with a key: Encryption

Each method solves a different problem.

4. Why is data in use typically hardest to protect?

  • It must be in readable form in memory while being processed
  • It is always stored on tape
  • It is never present on endpoints
  • It cannot be classified
Answer and explanation
  • Correct: It must be in readable form in memory while being processed. Decrypted data is exposed during processing.
  • Incorrect: It is always stored on tape. Tape is storage.
  • Incorrect: It is never present on endpoints. It may well be.
  • Incorrect: It cannot be classified. All data can be classified.

B. Product design assessment

Rate your work in the interactive app, where it counts toward design competency only.

1. Staff must verify a member's ID by comparing its last four digits and never need the full value. Which approach fits?

  • Server-side masking that returns only the last four digits
  • Client-side masking with the full value sent to the page
  • Hashing the value, then displaying the entire hash to staff
  • Encrypting at rest and showing the full value to all staff
Answer and explanation
  • Correct: Server-side masking that returns only the last four digits. The full value never reaches the browser, and the task still works.
  • Incorrect: Client-side masking with the full value sent to the page. The full value is exposed to anyone who inspects the response.
  • Incorrect: Hashing the value, then displaying the entire hash to staff. A hash can't be compared by eye with what a member says.
  • Incorrect: Encrypting at rest and showing the full value to all staff. Encryption at rest does not limit who can view it on screen.

6. Review and references

Common mistakes

  • Calling tokenization encryption. Tokens have no key relationship with the value.
  • Treating obfuscation or transposition as strong protection.

Summary

  • Know the type, state and classification of your data.
  • Masking, tokenization, hashing and encryption solve different problems.
  • Protect each state appropriately.
