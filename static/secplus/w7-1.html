Types of vulnerabilities and attack surfaces

Lesson 26 · Week 7 · Domain 2: Threats, Vulnerabilities, and Attacks · Objective 2.4 · Intermediate · about 120 min

Open this lesson in Atlas →

Direct product design relevance

1. Learn the concept

By the end, you can

  • Name the major vulnerability types and attack surfaces.
  • Explain race conditions and unsafe code practices.
  • Recognize shadow IT, rogue devices and stale credentials.

Why it exists and what problem it solves

You cannot fix a weakness you cannot name. This list is effectively a checklist of the places where real organizations get hurt, and many have nothing to do with sophisticated hacking.

In plain language

A vulnerability is any weak spot. Some are like a door with an old lock nobody makes keys for: unsupported products. Some are like a door the landlord does not know exists: shadow IT. Some are a key taped next to the lock: hardcoded secrets.

2. Technical deep dive

System weaknesses: unsupported products no longer receive vendor fixes. Unpatched systems have fixes available that were not applied. Obsolete systems are outdated and may be past useful life. Unmanaged systems are not tracked by IT, so they miss updates and monitoring. Open ports and services expose functionality that may not be needed. Operating system (OS) based vulnerabilities are flaws in the OS itself. Virtualization vulnerabilities include VM escape, where code breaks out of a guest into the host, and resource reuse between VMs.

Application weaknesses: a race condition happens when the result depends on the timing of events. In a time-of-check (TOC) to time-of-use (TOU) flaw, a system checks something, and the thing changes before it is used. A malicious update delivers harmful code through a normal update channel. Code weaknesses include hardcoded secrets, such as a password written into source code, and unsafe exception handling, which can expose internal details or leave a system in an insecure state when errors happen.

A zero-day is a vulnerability unknown to the vendor or with no fix available. Cryptographic vulnerabilities include weak algorithms, short keys and poor key handling. Unmanaged or stale credentials are accounts and passwords left active after they are no longer needed. Rogue devices are unauthorized devices attached to a network. Shadow IT is technology used without IT's knowledge or approval.

Other surfaces: wireless and low-powered communications, which often have weak security; large language models (LLMs), which accept natural language input and can be manipulated; identity providers, where one compromise can open access to many applications; mobile devices, which face loss, sideloading (installing apps from outside the official store) and jailbreaking or rooting; misconfiguration, among the most common causes of breaches; public repositories where code and secrets are accidentally published; and public object storage, such as cloud buckets left open.

Walkthrough: Tell apart three common findings

  1. A server has a patch available but it has not been installed: unpatched.
  2. An old OS gets no more patches from its maker: unsupported.
  3. A new attack hits a flaw for which no patch exists: zero-day.
  4. Each needs a different response: patch, replace or compensate, and detect or isolate.

Hands-on lab

Audit a sample configuration

About 35 min. A text editor, and your lab VM

  1. In your VM, create a file named app.py containing the line DB_PASSWORD = "Summer2026!".
  2. Run grep -rni password . in that folder and see the result.
  3. Rewrite the code to read the password from an environment variable, then repeat the search.
  4. List every port your VM has open using sudo ss -tuln, and write a reason for each.
  5. Delete the practice file when finished.

Expected: grep finds the hardcoded password, and the rewritten version no longer contains the secret itself.

This is what automated secrets scanning does at scale. Removing a secret from code is only half of the job, since a secret that was ever exposed must also be rotated.

Done when:

  • Your search found the secret before the fix and not after.
  • Each open port has a stated reason or a plan to close it.

3. See it in real products

Vulnerabilities often follow directly from product decisions. A sequential record ID in a URL invites people to try the next number. A file upload accepts more than it should. A self-service export has no limit. Designers see these features early, which is the cheapest moment to raise a concern.

In security operations

  • A developer pushes code containing a cloud key to a public repository, and automated scanners find it within minutes.
  • A department signs up for an online file-sharing app with a corporate card. That is shadow IT, and IT cannot protect what it does not know about.

4. Apply it as a Product Designer

Design brief: Threat model a feature before it ships

About 60 min

Scenario: Your team is adding public file requests to a contract tool: a customer creates a link, and outside people upload documents to it with no account.

Problem statement: The feature is specified only as a happy path. Nobody has examined who could misuse it or what it exposes.

Your design task:

  • Draw a simple data flow for the feature, including the trust boundaries.
  • Use the four questions: what are we building, what can go wrong, what will we do about it, did we do enough.
  • List at least five abuse cases and rank them.
  • Change your design to address the top three.

Technical security constraints:

  • Uploaders are unauthenticated, so uploaded content must be treated as untrusted.
  • Each link belongs to one customer, and other customers' data must stay unreachable.
  • Links can be guessed or forwarded unless they are long, random and revocable.

User needs:

  • Customers need to collect documents from people without accounts.
  • Uploaders need to know their upload arrived safely.
  • Reviewers need to open uploads without risk.

Expected deliverable: A data flow diagram, a ranked abuse-case list, and revised screens for the top three risks.

Evaluation criteria:

  • The diagram shows trust boundaries and treats uploads as untrusted.
  • Abuse cases go beyond attackers to include mistakes and misuse by legitimate users.
  • Safeguards such as link expiry appear as usable controls rather than buried settings.
  • Each top risk has an owner and a decision: fix, reduce, accept or defer.

Senior-level considerations:

  • Run a threat model with engineering and security in the room, because a designer's list is only an input to that process.
  • Record accepted risks with a named owner, so that a deferral is a decision and not an accident.

A design review is not a security sign-off. Have security engineers confirm technical decisions.

Questions a Senior Product Designer should ask

Engineering:

  • How is ownership checked on each object a user requests?
  • What are the file type and size limits, and where are they enforced?

Security:

  • Which parts of this feature fall under our threat modeling process?

Product:

  • Could this feature's value be reduced if we limit it, and by how much?

5. Test your understanding

A. Security+ technical assessment

Exam-style scenario: A review finds a Windows server running a version that Microsoft no longer supports. It cannot be replaced for a year. What is the vulnerability type, and what should be done meanwhile?

Compare your reasoning

An unsupported product. Because no patches are coming, the organization should apply compensating controls such as isolation, strict firewall rules and increased monitoring, and record the risk until the replacement happens.

1. A team uses an unapproved cloud app to share files. What is this?

  • Shadow IT
  • A zero-day
  • A race condition
  • An access vestibule
Answer and explanation
  • Correct: Shadow IT. It is technology used without IT's approval.
  • Incorrect: A zero-day. A zero-day is a flaw with no fix.
  • Incorrect: A race condition. This is a timing flaw in software.
  • Incorrect: An access vestibule. This is a physical entry control.

2. Which best describes a zero-day vulnerability?

  • A flaw that has no available vendor fix
  • A flaw that was patched last year
  • A vulnerability that scores 0.0 in CVSS
  • A misconfigured firewall rule
Answer and explanation
  • Correct: A flaw that has no available vendor fix. Defenders have had no time to patch.
  • Incorrect: A flaw that was patched last year. That would be an unpatched or fixed flaw.
  • Incorrect: A vulnerability that scores 0.0 in CVSS. That would mean no severity.
  • Incorrect: A misconfigured firewall rule. This is misconfiguration.

3. A program checks that a user may open a file, then opens it. Between those steps, the file is swapped for a sensitive one. What is this?

  • A time-of-check to time-of-use race condition
  • A buffer overflow
  • A hardcoded secret
  • Directory traversal
Answer and explanation
  • Correct: A time-of-check to time-of-use race condition. The resource changed between the check and its use.
  • Incorrect: A buffer overflow. That involves writing past a memory boundary.
  • Incorrect: A hardcoded secret. No embedded credential is involved.
  • Incorrect: Directory traversal. That manipulates file paths in requests.

4. Why are accounts of former contractors a serious risk?

  • They can give attackers valid access without needing to exploit anything
  • They slow down the file server
  • They prevent patches being applied
  • They use too much storage
Answer and explanation
  • Correct: They can give attackers valid access without needing to exploit anything. Unmanaged or stale credentials still work.
  • Incorrect: They slow down the file server. Performance is not the concern.
  • Incorrect: They prevent patches being applied. They have no such effect.
  • Incorrect: They use too much storage. Storage is not the issue.

5. Which are examples of misconfiguration or exposure? Choose two.

  • A cloud bucket left open to the public
  • A cloud key committed to a public repository
  • A fully patched and monitored server
  • An approved laptop using disk encryption
Answer and explanation
  • Correct: A cloud bucket left open to the public. Public object storage is a common exposure.
  • Correct: A cloud key committed to a public repository. This exposes a secret.
  • Incorrect: A fully patched and monitored server. This is not a weakness in itself.
  • Incorrect: An approved laptop using disk encryption. This is a protective control.

B. Product design assessment

Rate your work in the interactive app, where it counts toward design competency only.

1. A URL ends /invoice/1042. Changing it to 1043 shows another customer's invoice. Which response addresses the actual cause?

  • The server must check that the requester may access each object
  • Replace the numbers with long random identifiers alone
  • Remove the invoice number from the page design
  • Show a warning that invoices are private to customers
Answer and explanation
  • Correct: The server must check that the requester may access each object. This is missing authorization, so it has to be enforced on every request.
  • Incorrect: Replace the numbers with long random identifiers alone. Unguessable IDs reduce discovery, but access checks are still absent.
  • Incorrect: Remove the invoice number from the page design. Hiding the number leaves the request itself working as before.
  • Incorrect: Show a warning that invoices are private to customers. A warning does nothing to stop the request succeeding.

6. Review and references

Common mistakes

  • Confusing unpatched with unsupported. One has a fix waiting, and the other will never get one.
  • Removing a leaked secret from code but not rotating it.

Summary

  • Weaknesses include software, configuration, people and processes.
  • Timing flaws, hardcoded secrets and misconfiguration recur constantly.
  • Anything unknown to IT cannot be protected by IT.

What is the difference between unpatched and unsupported?

Unpatched means a fix exists but was not applied, and unsupported means no fixes are being produced.
