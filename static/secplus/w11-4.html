Access control models, MFA and passwords

Lesson 45 · Week 11 · Domain 4: Security Operations · Objective 4.5 · Intermediate · about 120 min

Open this lesson in Atlas →

Direct product design relevance

1. Learn the concept

By the end, you can

  • Compare access control models.
  • Choose MFA factors and understand their strengths.
  • Apply current password guidance.

Why it exists and what problem it solves

Most identity attacks succeed through weak or reused credentials and excessive permissions. Picking the right model and factors closes those paths.

In plain language

Role-based access is like staff uniforms: nurses get nurse access. Discretionary access is like owning your diary: you decide who reads it. Mandatory access is like a military clearance, which the owner cannot change. Just-in-time access is a key checked out for one hour.

2. Technical deep dive

In role-based access control, users are assigned roles, roles hold permissions, and a person's access is the combination of their roles. With role inheritance, a senior role automatically receives the permissions of a junior role, so an administrator role can include everything an editor can do. Least privilege means giving each role only what the job needs. Access enforcement must happen on the server for every request: hiding a button changes what users see, not what they can do.

Access control models include role-based (permissions follow job roles), rule-based (conditions apply, such as firewall rules), mandatory (the system enforces labels and clearances), discretionary (owners decide), time-based (access is limited to certain hours) and just-in-time (elevated access is granted temporarily when needed). Attribute-based access control (ABAC), which decides using attributes of the user, resource and context, is not in the current list but is common. Privileged access management (PAM) tools secure and broker admin access.

Access management includes authentication, and policies that are logical/technical (enforced by systems) or administrative/business (rules set by the organization). An access review periodically confirms that people still need their permissions.

Multifactor authentication uses different factor types. A hard token is a physical device. A soft token is an app. Biometrics measure a body feature. A one-time password (OTP) is valid once or for a short time. A backup code is a pre-generated recovery code. Phishing-resistant options such as FIDO2 security keys and passkeys are stronger than SMS or push prompts.

Password concepts: a passkey is a FIDO credential based on public key cryptography, bound to the real site, so it resists phishing. Passwordless authentication replaces passwords with such methods. Password managers generate and store unique passwords. NIST SP 800-63B-4 says that passwords used alone must be at least 15 characters, and that verifiers should check against lists of compromised values, should not impose composition rules and should not force periodic changes unless there is evidence of compromise. Many organizations still enforce complexity, expiration and minimum age, and the exam may refer to them. Password best practices cover length, complexity, reuse, expiration, age (how long a password must be kept before it can be changed), compromised credential monitoring, account auditing and a policy report that shows compliance.

Walkthrough: Select a factor combination

  1. A password plus SMS is better than a password alone, but SMS can be intercepted or swapped.
  2. A password plus an authenticator app is stronger.
  3. Hardware security keys or passkeys are resistant to phishing.
  4. Keep backup codes secure for recovery.

3. See it in real products

Workspace products usually begin with admin and member, and then customers need billing-only roles, guests, auditors and project-level overrides. Every addition makes it harder to answer the simple question "who can do what?". Inheritance adds to the difficulty, because effective access may not match what is shown on a person's profile.

In security operations

  • Administrators request admin rights for one hour using a PAM tool, and every session is recorded.
  • A passkey will not work on a look-alike phishing site because it is bound to the real domain.

4. Apply it as a Product Designer

Design brief: Design enterprise role and permission management

About 60 min

Scenario: A workspace communications product has an owner, admin and member model. Enterprise customers want custom roles, channel-level permissions, guests and auditor access, and security teams want to prove who has access.

Problem statement: Permissions have grown ad hoc, and administrators cannot tell what a role grants or why a specific person has access.

Your design task:

  • Build a permission matrix for at least five roles and twelve actions.
  • Design role creation that shows impact before saving.
  • Design a view explaining why a person has a specific permission.
  • Design bulk changes and an access review.

Technical security constraints:

  • Enforcement happens on the server for every request, whatever the interface displays.
  • The product must always keep at least one owner or admin account.
  • Inherited permissions may conflict, so a clear rule must decide the result.

User needs:

  • Administrators need to apply least privilege without understanding every action.
  • Auditors need read access with no ability to change anything.
  • Team leads need to manage their own area and nothing wider.

Expected deliverable: A permission matrix and designs for role editing, effective access and access review.

Evaluation criteria:

  • The matrix applies least privilege and states how inheritance and conflicts resolve.
  • Privilege escalation is covered, including an admin granting themselves more access.
  • An administrator can explain why a person has a specific permission.
  • The model considers scale: hundreds of custom roles, migrations and how new features add permissions.

Senior-level considerations:

  • Every new permission is a long-term cost, so challenge a custom role when a simpler model would serve.
  • Agree the rule for conflicting permissions with engineering before you draw any screens.

A design review is not a security sign-off. Have security engineers confirm technical decisions.

Questions a Senior Product Designer should ask

Engineering:

  • Is access evaluated per workspace, per project or per object?
  • How is a user's effective permission calculated when roles combine?

Security:

  • Which permissions must be separated, such as administering users and approving payments?

Product:

  • Which roles do customers keep asking us to add?

5. Test your understanding

A. Security+ technical assessment

Exam-style scenario: Administrators currently hold permanent domain administrator rights. Audit asks for reduced standing privilege. What should be implemented?

Compare your reasoning

Just-in-time privileged access, typically through PAM, granting time-limited elevation with approval and logging.

1. Permissions assigned by job function describe which model?

  • Role-based
  • Discretionary
  • Mandatory
  • Time-based
Answer and explanation
  • Correct: Role-based. Permissions follow roles.
  • Incorrect: Discretionary. Here, owners decide.
  • Incorrect: Mandatory. Here, labels decide.
  • Incorrect: Time-based. Here, time decides.

2. Which is the most phishing-resistant option?

  • A FIDO2 security key
  • SMS code
  • A second password
  • A security question
Answer and explanation
  • Correct: A FIDO2 security key. It is bound to the correct site.
  • Incorrect: SMS code. It can be phished or intercepted.
  • Incorrect: A second password. This is the same factor.
  • Incorrect: A security question. This is something you know.

3. According to NIST SP 800-63B-4, which practice is recommended?

  • Check new passwords against lists of compromised values
  • Force changes every 30 days
  • Require a mix of symbols and capitals
  • Limit passwords to 8 characters
Answer and explanation
  • Correct: Check new passwords against lists of compromised values. This addresses a major real-world risk.
  • Incorrect: Force changes every 30 days. NIST says not to require periodic changes.
  • Incorrect: Require a mix of symbols and capitals. NIST says not to impose composition rules.
  • Incorrect: Limit passwords to 8 characters. Longer passwords should be permitted.

4. A system prevents a file's owner from sharing it because of its classification label. Which model is this?

  • Mandatory
  • Discretionary
  • Role-based
  • Rule-based
Answer and explanation
  • Correct: Mandatory. The system's labels override owner discretion.
  • Incorrect: Discretionary. There, the owner could share.
  • Incorrect: Role-based. The scenario does not concern roles.
  • Incorrect: Rule-based. The scenario relies on classification labels.

5. Match each example to its authentication factor type.

Correct matches
  • A hardware security key: Something you have
  • A fingerprint: Something you are
  • A PIN: Something you know

Factors are distinguished by their type, and combining different types creates MFA.

6. Why perform regular access reviews?

  • To remove permissions no longer needed
  • To increase password complexity
  • To test backups
  • To scan for open ports
Answer and explanation
  • Correct: To remove permissions no longer needed. This counters privilege creep.
  • Incorrect: To increase password complexity. This is a separate control.
  • Incorrect: To test backups. This is restoration testing.
  • Incorrect: To scan for open ports. This is scanning.

B. Product design assessment

Rate your work in the interactive app, where it counts toward design competency only.

1. Customers want a "Billing Admin" role. Today only full admins can see invoices. What is the best approach?

  • Create a narrow role limited to billing actions
  • Make all billing staff full admins with a usage policy
  • Hide the admin menu items for these billing users
  • Let any member view invoices so that nobody is blocked
Answer and explanation
  • Correct: Create a narrow role limited to billing actions. It provides what the job requires and nothing beyond it.
  • Incorrect: Make all billing staff full admins with a usage policy. A policy doesn't limit what the access technically allows.
  • Incorrect: Hide the admin menu items for these billing users. Interface hiding doesn't remove their server-side access.
  • Incorrect: Let any member view invoices so that nobody is blocked. This exposes financial data to people with no need for it.

6. Review and references

Common mistakes

  • Treating two passwords as MFA.
  • Assuming strict complexity and frequent expiry are current best practice. NIST now advises length and breach checks.

Summary

  • Match the access model to the need.
  • Prefer phishing-resistant authentication.
  • Favour length, uniqueness and breach checks.
