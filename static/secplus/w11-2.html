Security alerting and monitoring

Lesson 43 · Week 11 · Domain 4: Security Operations · Objective 4.4 · Intermediate · about 120 min

Open this lesson in Atlas →

Direct product design relevance

1. Learn the concept

By the end, you can

  • Explain the roles of SIEM and related tools.
  • Compare NetFlow, SNMP, syslog and SCAP.
  • Tune alerts to reduce noise.

Why it exists and what problem it solves

Analysts live inside these tools. Too few alerts means missing attacks. Too many means people stop paying attention.

In plain language

Monitoring is like a building's security desk. Cameras, door sensors and alarms all feed one room. A SIEM is that room. Alert tuning makes sure the alarm does not go off each time someone opens a window.

2. Technical deep dive

Monitoring covers systems, applications and infrastructure. Activities include log aggregation (collecting logs in one place), alerting, scanning, archiving (retaining data for later), reporting and alert tuning (adjusting rules to reduce false positives).

Tools include benchmarks, which define secure configuration targets; agents, installed on a device, and agentless collection, which reads remotely; security information and event management (SIEM), which aggregates and correlates events; antivirus; DLP; vulnerability scanners; orchestration; and a packet analyzer such as Wireshark, which examines traffic in detail. Security orchestration, automation and response (SOAR) acts on alerts through playbooks. A SIEM finds and correlates, while SOAR takes the resulting actions.

Protocols: NetFlow records metadata about traffic flows but not content. Simple Network Management Protocol (SNMP) monitors and manages devices. syslog is a standard for sending log messages. Security Content Automation Protocol (SCAP) standardizes how vulnerability and configuration information is expressed, so tools can share it. Port mirroring copies traffic to a monitoring port. Dashboards summarize status. Automated alerts notify staff without someone watching. Network management systems monitor device health.

Walkthrough: Tune a noisy alert

  1. Find out how often the alert fires and how often it is real.
  2. Identify the benign cause, for example a scheduled backup.
  3. Add a precise exception, not a broad one.
  4. Monitor to confirm real events are still detected.
  5. Document why the exception exists.

Hands-on lab

Aggregate and search logs

About 40 min. journalctl and grep in your lab VM

  1. Run sudo journalctl --since "1 hour ago" -p warning to filter logs.
  2. Write a small shell one-liner that counts failed sudo attempts.
  3. Open Wireshark with a sample capture from the Wireshark wiki and find the conversation statistics.
  4. Decide what you would alert on, and write the rule in plain language.

Expected: A filtered list, a count and an alert written with a threshold.

A rule is only useful if you can say what triggers it and why that matters.

Done when:

  • You produced a count from a log search.
  • Your alert rule states a threshold and a reason.

3. See it in real products

Security monitoring tools turn logs into alerts and alerts into investigations. Analysts suffer from alert fatigue, so a dashboard that adds noise makes the organization less safe. Good design shows why an alert fired, gathers related events and supports a clear decision.

In security operations

  • A SIEM correlates a failed VPN login, a successful one and a large download, and raises one high-priority alert.
  • An alert fires hundreds of times a day for a harmless backup process, so analysts begin ignoring it. Tuning fixes that.

4. Apply it as a Product Designer

Design brief: Design a monitoring dashboard and investigation view

About 60 min

Scenario: A mid-sized company's IT team uses a product's security center to review sign-in and admin activity. They have no dedicated analysts and receive 300 alerts a day.

Problem statement: Alerts appear as an undifferentiated feed with no context, so real incidents are missed.

Your design task:

  • Define what the overview must answer in the first ten seconds.
  • Design an alert detail with the reason, related events, affected accounts and severity.
  • Design triage states: new, investigating, escalated, closed with a reason.
  • Design tuning for a noisy rule, with safeguards.

Technical security constraints:

  • Logs have delays and gaps, so the interface must show data freshness.
  • Suppressing a rule can hide a true attack, so it must be logged and expire.
  • Investigators can see sensitive activity, so access must itself be audited.

User needs:

  • Generalist administrators need plain explanations.
  • Investigators need a timeline of related events.
  • Managers need to know whether alerts are being handled.

Expected deliverable: An overview, alert detail and triage design, with an explanation of how noise is reduced.

Evaluation criteria:

  • Freshness and gaps in log data are visible to the user.
  • Suppression can't quietly hide attacks.
  • The reason an alert fired is understandable without specialist knowledge.
  • Success is defined by outcomes such as time to triage, and not by the count of charts.

Senior-level considerations:

  • More data is not better, so ask analysts which decisions they make and design for those.
  • Decide who may view monitoring data, because the tool itself holds sensitive information.

A design review is not a security sign-off. Have security engineers confirm technical decisions.

Questions a Senior Product Designer should ask

Engineering:

  • Which fields are reliably available in each log source?
  • How long between an event and the alert?

Security:

  • What is our false positive rate, and which alerts are ignored most?

Product:

  • Is this tool for a security specialist or a general IT administrator?

5. Test your understanding

A. Security+ technical assessment

Exam-style scenario: An analyst must quickly see whether a host sent a large amount of data to an unfamiliar address, and packet captures are not available. Which data source helps most?

Compare your reasoning

NetFlow or similar flow data, which records who communicated, when and how much, without storing the content.

1. What is the main function of a SIEM?

  • Aggregating and correlating security events
  • Providing battery backup
  • Issuing certificates
  • Assigning IP addresses
Answer and explanation
  • Correct: Aggregating and correlating security events. It brings together logs and finds patterns.
  • Incorrect: Providing battery backup. This is a UPS.
  • Incorrect: Issuing certificates. This is a CA.
  • Incorrect: Assigning IP addresses. This is DHCP.

2. A system automatically disables an account and opens a ticket when an alert fires. Which technology is that?

  • SOAR
  • SNMP
  • SPF
  • NetFlow
Answer and explanation
  • Correct: SOAR. It automates response actions.
  • Incorrect: SNMP. This monitors devices.
  • Incorrect: SPF. This is email authentication.
  • Incorrect: NetFlow. This records flow metadata.

3. Match each protocol to its use.

Correct matches
  • NetFlow: Metadata about traffic flows
  • SNMP: Monitoring and managing devices
  • syslog: Sending log messages
  • SCAP: Standardized security content

Each one carries a different type of information.

4. How does a monitoring sensor receive a copy of switch traffic without being inline?

  • Port mirroring
  • OCSP stapling
  • A captive portal
  • Key escrow
Answer and explanation
  • Correct: Port mirroring. The switch copies traffic to the sensor's port.
  • Incorrect: OCSP stapling. This relates to certificates.
  • Incorrect: A captive portal. This handles guest access.
  • Incorrect: Key escrow. This stores keys.

5. A rule produces hundreds of harmless alerts. What is the best action?

  • Tune it with a precise exception and monitor the result
  • Disable all alerts
  • Ignore it, as analysts will get used to it
  • Delete the logs
Answer and explanation
  • Correct: Tune it with a precise exception and monitor the result. This reduces noise while keeping detection.
  • Incorrect: Disable all alerts. This removes detection.
  • Incorrect: Ignore it, as analysts will get used to it. Alert fatigue causes real events to be missed.
  • Incorrect: Delete the logs. This destroys evidence.

B. Product design assessment

Rate your work in the interactive app, where it counts toward design competency only.

1. A team closes most alerts without reading them. What change addresses the underlying problem?

  • Reduce noise and show why each alert fired
  • Use a brighter colour and sound for every single alert
  • Require a mandatory comment before each alert is closed
  • Show a larger total alert count on the main dashboard
Answer and explanation
  • Correct: Reduce noise and show why each alert fired. Fatigue comes from low-value alerts and missing context.
  • Incorrect: Use a brighter colour and sound for every single alert. Louder alerts add more noise and make the fatigue worse.
  • Incorrect: Require a mandatory comment before each alert is closed. This adds work without improving the alerts themselves.
  • Incorrect: Show a larger total alert count on the main dashboard. A bigger number does not help anyone decide what matters.
